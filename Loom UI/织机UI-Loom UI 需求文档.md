# Loom UI 需求文档

**文件名：** `UI/UI_REQUIREMENTS.md`

## 一、UI 的定位

Loom UI 是整个框架的界面构建与交互系统。

它负责绘制、布局、呈现和交互，使开发者能够通过脚本创建完整的用户界面，而不必重复编写大量底层 HTML、CSS 和事件处理代码。

UI 应当是一套可以独立使用、扩展和替换的系统。

它不负责具体业务逻辑，而是通过明确接口与 Core 和扩展脚本协作。

## 二、核心职责

### 2.1 绘制

UI 应能够绘制常见界面元素。

包括但不限于：

- 按钮。
- 输入框。
- 选择器。
- 开关。
- 列表。
- 标签。
- 卡片。
- 弹窗。
- 面板。
- 菜单。
- 图片及其他媒体内容。

基础组件应具有统一的使用方式和必要的属性描述。

### 2.2 布局

UI 应提供组织界面结构的能力。

包括：

- 水平和垂直排列。
- 网格布局。
- 嵌套布局。
- 组件组合。
- 尺寸控制。
- 间距控制。
- 对齐方式。
- 滚动区域。
- 响应式布局。

不应要求开发者通过大量重复代码手动排列基础组件。

### 2.3 呈现

UI 应能够展示：

- 静态文本。
- 动态数据。
- 运行状态。
- 操作结果。
- 错误反馈。
- 加载状态。
- 其他由扩展提供的内容。

UI 应能够响应数据变化，更新相应界面。

### 2.4 交互

UI 应能够接收并处理用户操作。

包括：

- 点击。
- 输入。
- 选择。
- 拖动。
- 长按。
- 滑动。
- 展开与折叠。
- 键盘操作。
- 其他适合的交互方式。

不同组件应能够定义自身的交互事件，并允许脚本绑定对应动作。

## 三、脚本与 UI 的双向联动

这是 Loom UI 的重要能力。

脚本可以：

- 创建 UI。
- 修改 UI 属性。
- 更新 UI 数据。
- 显示或隐藏组件。
- 添加或删除组件。
- 监听 UI 事件。
- 根据业务逻辑更新界面。

UI 也可以：

- 向脚本传递用户输入。
- 触发脚本定义的动作。
- 修改绑定的数据。
- 通知脚本用户操作结果。

UI 与脚本之间不应存在单向依赖。

界面状态与业务状态应有明确的区分，避免 UI 临时状态与扩展业务数据混为一体。

## 四、组件体系

### 4.1 基础组件

UI 应提供一组通用基础组件，作为复杂界面的构建基础。

基础组件应保持用途明确、接口统一。

### 4.2 自定义组件

扩展开发者应能够创建自己的 UI 组件。

自定义组件应能够：

- 定义自身属性。
- 定义输入和输出。
- 定义交互事件。
- 使用其他 UI 组件。
- 管理必要的内部状态。
- 被其他界面引用。
- 被其他扩展复用。

不应强制所有组件都由 Loom 官方预先提供。

### 4.3 复合组件

应允许通过多个基础组件组合出复杂组件。

复合组件可以保存、复用、嵌套和分享。

其内部结构原则上应保持可查看和可修改，不应因为组合就必然成为不可拆解的黑箱。

组件实例的内部状态默认相互独立，除非明确声明共享。

### 4.4 组件属性与描述

组件应具有可供系统理解的属性描述。

例如：

- 属性名称。
- 数据类型。
- 默认值。
- 可选范围。
- 是否允许修改。
- 是否必填。
- 对应事件。
- 输入和输出。

这些描述可以用于生成配置界面、组件编辑界面和开发文档。

## 五、动态 UI 与可视化编辑能力

UI 应在架构上支持动态创建和修改界面。

包括：

- 运行时创建组件。
- 修改组件属性。
- 替换组件。
- 删除组件。
- 修改组件之间的布局关系。
- 动态嵌套组件。
- 读取组件描述。
- 将界面结构保存为可复用资源。

未来应允许基于 Loom UI 自身构建可视化 UI 编辑器。

可视化编辑器不要求成为 UI 的内置功能，可以作为普通 Loom 扩展实现。

但 UI 的基础接口和组件描述机制不应妨碍这一目标。

对于自由编写的 JavaScript 逻辑，不要求全部自动转换为可视化节点。

声明式界面结构应尽可能支持读取、编辑和重新生成。

## 六、与 Core 的协作

UI 不应自行承担 Core 的业务职责。

需要读取数据或执行操作时，应通过约定接口向 Core 或对应扩展请求。

UI 应能够接收 Core 返回的数据、状态和执行结果。

界面中的用户操作应能够转换成明确的请求或事件。

## 七、与 SillyTavern 的协作

UI 应能够在 SillyTavern 环境中正常运行。

应考虑多种界面呈现方式：

- 独立面板。
- 弹窗。
- 悬浮界面。
- 侧边栏。
- 嵌入酒馆已有页面。
- 嵌入适合的原生交互区域。

UI 应尽量复用酒馆已有的界面能力，但不能将自身的组件体系完全绑定到某一个酒馆原生界面上。

在适合的情况下，应允许使用 Loom UI 作为交互入口，调用酒馆原生功能。

例如使用 Loom UI 编辑和提交世界书数据，而实际保存由适当的酒馆接口完成。

具体嵌入位置和原生接口可用性应根据宿主实际情况验证。

## 八、视觉与使用体验

UI 应具有统一的视觉和交互规范。

应考虑：

- 桌面端和移动端。
- 不同屏幕尺寸。
- 紧凑布局。
- 可配置样式。
- 主题适配。
- 可复用的交互模式。
- 复杂界面的可维护性。

不应为了统一外观而限制开发者制作具有特殊视觉风格的自定义组件。

## 九、可扩展性与兼容性

UI 应允许新增组件、布局方式、渲染方式和交互模式。

新增组件应遵循统一接口。

修改通用组件时，应考虑所有使用该组件的界面，避免只修复单个实例而破坏其他实例。

UI 应尽量保持与 Core 解耦，未来允许替换 UI 实现，而不要求所有上层扩展重新编写业务逻辑。

## 十、非目标

UI 不负责：

- 具体业务数据处理。
- 世界书触发规则判断。
- 角色管理业务逻辑。
- 聊天自动化业务逻辑。
- 扩展之间的业务协调。
- 宿主数据的底层读取和写入。

这些职责应由 Core、Host Adapter 或上层扩展承担。

---

**文档性质：** UI 的组件、布局、呈现、交互和扩展需求。

**约束：** UI 应是一套通用界面构建系统，而不是为某个特定扩展制作的固定界面。
