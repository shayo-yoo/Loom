# CHG-20261121-016

- Date: 2026-11-21 (Asia/Shanghai)
- Type: FEATURE, API, UI, TEST, DOCS
- Requirement / motivation: The UI requirements ask for §2.1 drawing (images and dialogs were missing), §2.3 responding to data changes, §4.3 composite components that can be saved and reused, and §5 "declarative interface structures should be readable, editable and regenerable" — the stated prerequisite for building a visual UI editor on top of Loom UI. Before this change every mutation rebuilt the entire DOM tree (so the components' `update` functions were dead code), there was no serialization path, and four of the ten primitive kinds in §2.1 did not exist.
- Stage: UI system deepening, run in parallel with the extension loader (CHG-20261121-015). Owned by a delegated worker under explicit file ownership; reviewed, integrated, documented and browser-verified by the lead.

## Changes

### Partial updates (`Loom UI/views.js`)

- Mounting records every node element by tree path (`data-loom-path`), so `setProps(path, props)` can call the component's declared `update` instead of rebuilding. The DOM node is reused and event handlers stay attached — `update` was previously never called.
- Components without `update`, or paths that are not mounted, fall back to a full rebuild.
- If `update` throws (for example an unsafe image `src`), the tree props are rolled back to their previous values, so the declared state and the DOM cannot disagree.
- Structural changes still rebuild, but focus, text selection, component `scrollTop` and window scroll are captured before the swap and restored on the equivalent node afterwards.

### Serialization (prerequisite for a visual editor)

- `view-tree.js`: `serializeNode(node)` — recursive, handler-free, JSON-compatible output; non-JSON prop values are dropped, `bigint` throws, the input tree is not mutated.
- `views.js`: `serializeView(viewId)`, `createViewFromSerialized(extensionId, serialized, options?)`, and `view.serialize()`.
- `createViewFromSerialized` rejects any `on` at any level, so a serialized resource cannot smuggle behaviour back in.
- `LoomUI` facade exposes `serializeView`, `serializeNode`, `createViewFromSerialized` (additive).

### New components (`Loom UI/builtin-components.js`)

- `image` — `src`/`alt`/`caption`/`fit`, lazy, emits `load`/`error`; protocol allowlist (`http:`, `https:`, `data:`, `blob:`) enforced on mount and update, exported as `isSafeImageSource`.
- `tabs` — container with `labels` + child panels, `active`, emits `change({ index })`; slot-based mounting gives each child its own panel container.
- `modal` — controlled dialog with `open`/`title`/`closable`, emits `close`; focus moves into the dialog on open, Escape is handled inside it.
- `menu` — `items: [{ id, label }]`, emits `select({ id })`.
- Styles use theme variables, 44px tap targets, a literal 600px breakpoint, safe-area insets and `prefers-reduced-motion`.

## Validation

- `npm test`: **140 tests pass**, of which **54 are UI tests** (33 before, +21 net; no existing assertion was weakened). New coverage includes in-place `setProps` reusing the same node, fallback rebuild, focus/selection/scroll restoration, serialization round-trip (§ deep-equal to `describe()`, no `on`, JSON safe), rejection of handler-bearing trees, and the four new components' mount/update/event/safety behaviour.
- `npm run verify:browser`: **65/65 checks pass** against a live SillyTavern. The new probe mounts a view containing `text`/`tabs`/`image`/`modal`/`menu` in a real browser, asserts it renders, asserts an unsafe `javascript:` image source is rejected, round-trips through `serializeView` → JSON → `createViewFromSerialized` (same serialized output, no handlers), and asserts `setProps` updates the **same DOM node** — i.e. the partial-update claim is verified in a browser, not only in the DOM fixture.
- The DOM fixture is a hand-written stand-in, not jsdom; layout, CSS cascade and media queries are asserted as stylesheet text, so real rendering still depends on the browser probe.

## Failed checks and corrections (recorded, none hidden)

1. The delegated report claimed the pre-change UI suite had 26 tests; the measured count was 33. The final counts above use the measured numbers.
2. An integration edit accidentally renamed `renderCapabilities` to `renderCapacityStatus`, breaking the capabilities renderer; caught by `node --check` plus a function-name grep and fixed before running tests.
3. The first browser run of the new lifecycle probe failed activation with `DEPENDENCY_MISSING` because the host adapter is `unmanaged`, not `active`. The fix was a design correction in the loader (unmanaged counts as satisfied), not a test relaxation — see CHG-20261121-015.

## Risks / outstanding

- `update` is only used for prop changes; child-list changes still rebuild the whole view. There is no subtree-level reconciliation, so a large dynamic list will still be re-created on every structural change.
- Focus restoration is best-effort: focus inside a component's internal element (for example a toggle's `<input>`) is restored to the enclosing component element, which may not be focusable.
- Serialization cannot preserve handlers or function-valued props; a re-mounted view is inert until the caller re-attaches behaviour.
- `tabs` keeps local active state independent of the declared `active` prop until the caller updates it, which can surprise a caller that expects controlled behaviour.
- `modal` has no focus trap, and no document-level Escape listener exists because the view engine still has no unmount hook — the real blocker for menus that close on outside click and for tooltips.
- Pre-existing CSS class mismatches were found but **not** fixed (`.loom-capability_id`, `.loom-identity_member`, `.loom-panel_actions` do not match the markup, so those rules never apply). Recorded rather than silently changed, because they belong to earlier increments.
- `updateCard` leaves an empty title node when `title` becomes empty (pre-existing).
