# CHG-20261124-049

- Date: 2026-11-24 (Asia/Shanghai)
- Type: FIX, ARCH, TEST, DOCS
- Requirement / motivation: making the panel actually visible exposed a family of problems around *when* Loom loads and how the verification harness observes the host. Both were fixed, and one of them changed a product decision (extension loading order).
- Stage: continuation of `feature/character-panel-demo`, version 0.41.0.

## 1. Loom loads too late (product change)

Loom's `manifest.json` declared `loading_order: 950`, near the very end. SillyTavern activates third-party extensions in that order, so **any extension that stalls during activation blocks Loom entirely**. That is exactly what happened: a third-party extension with a network version check held the "Initializing…" overlay, Loom never registered, and the whole framework appeared broken when it was only never started.

Loom is infrastructure: other extensions may depend on it, and it must not be hostage to one slow neighbour. `loading_order` is now **-500** — after the one extension that deliberately loads first (-1000), before everything else.

Evidence: with 950, `window.Loom` was still `undefined` after 100 s of polling; with -500 it appears in ~18 s and is available while the overlay is still up.

## 2. `rescan` refused to re-import a registered-but-inactive package

`rescanExtensions` skipped only `state === 'active'` and then imported the rest, so a package that was registered but inactive hit the loader's "already loaded" error and stayed broken. It now unloads first — the same idempotent path `setExtensionEnabled` uses.

## 3. The harness could not tell "host is initializing" from "Loom is broken"

- Navigation and reload probes now wait for SillyTavern's init overlay to clear (`waitForHostReady`, 150 s budget) after **every** navigation, not just at startup. Under the overlay the page is inert: clicks land on the dialog and the debounced settings save is deferred, which produced three unrelated-looking failures (disabled flag not flushed, script still registered after reload, panel not hit-testable).
- The Chrome profile removal retries instead of throwing `EBUSY` after the results have already been recorded.
- Scratch-book deletion moved **before** grant revocation in cleanup: removal needs the `host.worldinfo.*` grants that the next step revokes, so the order decided whether the books survived.
- The scratch chat directory is also removed at the end, after the probes stop saving into it (SillyTavern re-creates the directory on a late save).

## Verification

- `npm test`: 300 tests pass (unchanged by this round).
- `npm run verify:browser`: **217/217 checks pass**, three consecutive runs, exit code 0.

- A save response can belong to a request that started before a state change, so the script-disable probe now also confirms the stored `enabled: false` before reloading. That removed an intermittent "a disabled script stays off after a reload" failure (4 of 5 runs passed before the precondition).

## Known gaps

- The harness still cannot exercise `panel.show`'s real append path (recorded in CHG-048); it is verified by hand.
- `loading_order: -500` means Loom's UI elements mount before SillyTavern finishes building `#extensions_settings`; the existing retry in `initialize` covers it, and the harness proves the panel and menu entry still appear.
- SillyTavern's own init duration is outside our control; a harder stall would make the harness fail with an explicit `SillyTavern init` timeout rather than cascading failures, which is the intended behaviour.

## Direct scope

`manifest.json`, `Loom UI/index.js`, `tests/browser/verify.mjs`, governance docs, version markers.
