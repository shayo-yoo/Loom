# CHG-20261122-042

- Date: 2026-11-22 (Asia/Shanghai)
- Type: FEATURE, API, TEST, DOCS
- Requirement / motivation: second half of the "注入" list. An extension could float its own DOM anywhere, but it could not put a view **inside** a SillyTavern panel (the extension-settings column, the wand menu), which is where a feature belongs when it is part of configuring the host rather than a standalone tool.
- Stage: branch `feature/host-injection`, second batch.

## Design

`LoomUI.mountToSlot(extensionId, slot, viewOptions)` renders a normal Loom view into a named host container:

| Slot | Container |
|---|---|
| `settings` | `#extensions_settings` |
| `settings2` | `#extensions_settings2` |
| `menu` | `#extensionsMenu` |
| `leftNav` | `#left-nav-panel` |

Rules, and why:

- **Allowlist, not a selector.** An extension cannot ask Loom to render into an arbitrary host element, and a host rename is a one-line change in `slots.js` instead of a hunt through extensions. An unknown slot throws with the known names.
- **Lazy.** A container may not exist yet (the panel is built after boot); `mountToSlot` returns `null` and the caller mounts again when it appears. No polling, no timers.
- **One mount per (extension, slot).** Re-mounting replaces the previous wrapper rather than stacking.
- **Cleanup on unregister.** Each mount is registered as an extension cleanup, so unloading an extension cannot leave orphaned UI inside SillyTavern's own panels (verified in both the unit suite and the browser).
- The view is a normal `createView` call, so the wrapper only adds `.loom-slot` and two data attributes; everything else (props, events, reconciliation, serialization) is unchanged.

## Direct scope

`Loom UI/slots.js` (new), `Loom UI/slots.test.js` (new), `Loom UI/index.js` (facade), `Loom UI/style.css`, `tests/browser/verify.mjs`, docs, version markers.

## Horizontal impact

- SYNC: the facade gains `slots` (the frozen slot table), `mountToSlot`, `unmountFromSlot`, `listSlotMounts`, all following the existing `(extensionId?, ...)` overload pattern so `loom-ui` itself can call them without an id.
- ADAPT: `slots.js` imports `addCleanup` from Core directly, because a cleanup must be owned by the mounting extension, not by `loom-ui`.
- NO-CHANGE: floating panels (the Loom panel and the manager) keep owning their own DOM; this does not migrate them.

## Verification

- `npm test`: **263 tests pass** (+4: mount into an allowlisted container, lazy mount and replacement, unmount and unknown-slot rejection, cleanup on unregister).
- `npm run verify:browser`: **193/193 checks pass** (three consecutive runs). New: a view mounts into the real `#extensions_settings`, is listed, disappears on unmount, and disappears again after the owning extension unregisters; an unknown slot is rejected.

## Risks / outstanding

- The four containers are what SillyTavern 1.19 renders; a host upgrade may rename or restructure them. The slot table is the single place to fix, and `mountToSlot` returning `null` means a rename degrades to "nothing renders" instead of throwing.
- Sibling load order matters: a mounted view is appended last, so a host that reorders its own children could move it.
- There is no styling contract with the host — a mounted view inherits SillyTavern's panel styles, which may need per-slot CSS from the extension.
