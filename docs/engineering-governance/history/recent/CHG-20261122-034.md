The user also reported that Loom had no script loading and asked whether mobile was adapted. - Stage: new feature branch `feature/extension-and-script-management`, one batch committed after verification and merged into `main`.

## Extension management (no security work)

- **Enable/disable**: disabling unloads the extension (`deactivate` + unregister, which drops its capabilities, listeners and state) and records the id in `loom-ui` state (`disabledExtensions`); boot skips disabled packages. Enabling re-imports from the package source. Because browser modules cannot be evicted, "disable" is logical, not physical.
- **Reload**: `reloadExtension(id)` unloads and re-imports. Manual installs get a `loomReload` cache-busting parameter so editing a module file actually re-reads it (the module map would otherwise return the old instance).
- **Row detail**: each row now shows version, source (bundled/manual), state, declared permissions and dependencies, plus the failure message when present. Buttons are scoped per row (toggle, reload, remove).
- **Readiness**: `LoomUI.isReady()` reports whether boot finished (index fetched, packages imported, scripts run). The browser harness needs it, and the panel benefits from it.
- **Problems**: failed imports and script runs flow into `getInstallProblems()` and the panel's problem list instead of being silently swallowed.

## Scripts (lightweight extensions)

A script is module source kept in `loom-ui` state and imported through an object URL:

- No directory, no `manifest.json`, no index step. The author writes only `export default { activate, deactivate }`.
- Identity is generated (`script-<slug>`, collision-suffixed), so permissions, state, events, errors and unload behave like any extension.
- `saveScript` imports before persisting, so a broken script is not stored; saved scripts re-run on boot; `updateScript` reverts to the previous source if the new one fails to load.
- The panel has a source textarea, a name field, save-and-run, per-script re-run/delete, and a status line.
- **No sandbox**: this is a local loader with the same trust boundary as an extension. Recorded explicitly so nobody mistakes it for a security boundary.

## Mobile

- The world-book manager's fixed `400px` panel became `min(400px, calc(100vw - 32px))`, so it fits a phone without horizontal overflow.
- The harness gained a mobile pass: `Emulation.setDeviceMetricsOverride` at 390×844, then checks that `viewport.get` reports mobile, that Loom adds no horizontal overflow beyond the page baseline (the host page itself overflows 390 by 10px because of other extensions — recorded, and Loom's own elements are checked by scanning for right-edge offenders), that the manager panel fits, and that a permission button stays within 60px tall.
- This is an automated narrow-viewport check, **not** real-device testing: soft-keyboard viewport changes, touch gestures and long-list virtualisation remain unverified.

## Horizontal impact

- SYNC: `describeInstalled` gained `version`/`permissions`/`dependencies`; its test was extended, and `LoomUI.getInstalledExtensions()` consumers see the new fields.
- SYNC: script id generation moved to pure helpers (`scriptSlug`, `scriptIdFor`) so it is unit-testable; the UI delegates to them.
- ADAPT: the harness resets Loom-UI bookkeeping at the start of the install probe and after cleanup, because disabled packages and scripts now survive reloads and a previous run could otherwise change the starting state. This is a test-isolation fix, not a product change.
- ADAPT: the mobile probe compares against the page's own baseline overflow; asserting zero overflow would fail because of unrelated third-party extensions.
- NO-CHANGE: capabilities, permissions model, host adapter, world/chat/character writes.

- `npm test`: **243 tests pass** (241 before; +2 pure script-id/metadata tests).
- `npm run verify:browser`: **166/166 checks pass**. New: disable persists across a reload and boot skips the package; enable restores it and the capability runs; reload re-registers; a pasted script runs, registers a capability, survives a reload and is deleted cleanly; mobile viewport checks pass at 390px. Cleanup now also clears disabled/installed/script bookkeeping so reruns start clean.

## Risks / outstanding

- Disabling is logical: the module stays in the browser's module map, so a disabled extension's code remains loaded in memory and a reload is the only physical reset.
- Script sources live in SillyTavern settings; a very large script bloats the settings file and the client-side save payload.
- Scripts re-run on every boot with the stored source; there is no per-script enable flag (deleting is the only off switch) — a candidate for the next increment.
- The mobile check is synthetic. Real devices, soft keyboard, gestures and long lists are still untested; the page baseline overflow from other extensions is out of Loom's control.
- `getInstallProblems()` is in-memory only; problems reset on reload.
