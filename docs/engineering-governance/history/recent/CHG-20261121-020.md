# CHG-20261121-020

- Date: 2026-11-21 (Asia/Shanghai)
- Type: FIX, API, UI, TEST, DOCS
- Requirement / motivation: CHG-20261121-016 recorded that "`tabs` keeps local selection state independent of the declared `active` prop until the caller updates it, which can surprise a caller that expects controlled behaviour", and CHG-20261121-018 re-listed it as an open risk. A UI whose `describe()`/`serialize()` disagree with what is on screen cannot back a visual editor (UI requirements §5), and the framework already has one controlled component (`modal`), so two contradictory interaction models was a real inconsistency.
- Stage: self-planned goal `goal-957b8a59`, increment 2 (tabs/component polish), executed after keyed reconciliation.

## Change

`tabs` is now a **controlled** component, matching `modal`:

- Clicking a tab, or pressing Arrow/Home/End, emits `change({ index })` and moves focus to the target tab, but does **not** switch the visible panel by itself.
- The selected panel follows the declared `active` prop on every update, so the mounted tree, `describe()` and `serialize()` always describe what is actually shown.
- The tab strip keeps its ARIA state (`aria-selected`, `tabindex` roving) in sync with the declared value.

## Direct scope

`Loom UI/builtin-components.js`, `Loom UI/builtin-components.test.js`, `tests/browser/verify.mjs`, version markers, docs.

## Horizontal impact

- SYNC: the tabs unit test asserted local switching on click and keyboard; it now asserts the controlled contract (click reports intent, `setProps` selects) and keeps its structural assertions unchanged.
- SYNC: the browser probe gained three checks — click does not select, `setProps` selects, and the update reuses the same tab DOM nodes.
- NO-CHANGE: the consent prompt and panel do not use `tabs`; no production consumer depended on the local-switch behaviour.
- NO-CHANGE: `modal`, `menu`, `image` and the engine contract.
- CONFIRM: whether an uncontrolled convenience variant (`defaultActive`) is wanted. Not added: there is no consumer, and a second interaction model is what caused this inconsistency.

## Validation

- `npm test`: **172 tests pass** (unchanged count; one test rewritten to the new contract).
- `npm run verify:browser`: **83/83 checks pass** against a live SillyTavern, including the three new tabs checks.
- Manual reasoning recorded: a caller that wants click-to-switch now needs `on: { change: ({ payload }) => view.setProps([path], { active: payload.index }) }`; this is documented in `API_INDEX.md`.

## Failed checks and corrections (recorded, none hidden)

1. The first attempt made `active` an "override that only applies when the declared value changes", which sounded convenient but broke the controlled case: a caller rejecting a change (setting `active` back to the same value) would be ignored. Rejected as unpredictable; full control matches `modal` and keeps `describe()` honest.
2. The existing tabs test then failed on `aria-selected`, as expected; the contract, not the implementation, was the thing to change, and the rewritten test asserts both halves (intent, then caller selection).

## Risks / outstanding

- Tabs now require the caller to react to `change` for a click to have a visible effect; a caller that ignores the event sees no movement, which is correct but less forgiving than before.
- No `defaultActive`/uncontrolled mode; adding one later must not reintroduce local state that serialization cannot see.
- Tabs with more children than labels puts the extra children in an unreachable panel; with fewer children, empty panels appear. Still unvalidated (recorded in CHG-20261121-016).
