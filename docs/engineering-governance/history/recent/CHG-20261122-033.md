# CHG-20261122-033

- Date: 2026-11-22 (Asia/Shanghai)
- Type: FEATURE, API, TEST, DOCS
- Requirement / motivation: P1 item 3 from the stage goal — large libraries. `worlds.entries` returned at most 200 entries with no way to ask for the rest, and no way to find an entry without reading everything; the manager consequently loaded entire books into one select and had no search. The user's own library has 80+ books, so this is a real usability wall, not a hypothetical one.
- Stage: self-planned P1 goal `goal-c4b5aa5a`, item 3.

## Breaking change (recorded deliberately)

`worlds.entries` used to return a bare array. It now returns a page object:

```json
{ "name": "Lore", "total": 12, "offset": 0, "limit": 8, "hasMore": true, "entries": [ ... ] }
```

The empty case changed from `[]` to `{ total: 0, entries: [] }`. Nothing in the repository silently depends on the old shape after this change: the manager was rewritten in the same commit and every harness call site was migrated. The API index marks the change and the version is bumped to 0.30.0.

Why not a second capability (`worlds.entries.page`)? Two capabilities reading the same book would need to stay in sync and callers would have to pick one; the page object is the natural shape once pagination exists.

## Changes

### `worlds.entries`

- `offset` (integer ≥ 0, default 0) and `query` (string ≤ 200 chars) join the existing `limit` (1–200, default 200).
- `query` is a case-insensitive substring over `comment`, `keys`, `secondaryKeys` and the **visible** (truncated) content, so what a caller can search is exactly what a caller can see.
- `total` counts matches, not the page; `hasMore` is computed from the page end, so a caller does not have to do arithmetic on a possibly-short last page.
- An offset past the end returns an empty page with the correct `total` (not an error), and a negative offset is schema-rejected.
- Sorting is unchanged (`order`, then `uid`), so paging is stable across calls.

### `extensions/world-book-manager`

- The entry list is now paged through `worlds.entries` (page size 8) with **search input**, previous/next buttons and a `start–end / total` label.
- Full content is loaded only when an entry is selected, through `worlds.export` (cached per book). The list no longer needs the whole book.
- Saving now reloads the current page **without** overwriting the "已保存" status — the first version of the page reload cleared it, which the browser probe caught (the panel showed "已载入 12 个条目。" after a successful save).
- Changing a book resets search, offset, selection and the content cache; changing search resets the offset to 0.

## Direct scope

`Loom Host/index.js`, `Loom Host/index.test.js`, `extensions/world-book-manager/index.js`, `tests/browser/verify.mjs`, API index, project state, version markers.

## Horizontal impact

- SYNC: every harness call site that consumed the array shape (`worlds.entries` read-backs, rename content check, import round-trip, recreate-is-empty, entry CRUD) was migrated to `data.entries`/`data.total`.
- SYNC: the manager's page-size constant (`PAGE_SIZE = 8`) is a local UI choice; the capability's own limit stays 1–200.
- NO-CHANGE: `worlds.entry.*` writes (still uid-addressed), `worlds.export` (full raw book), `worlds.list`.
- CONFIRM (open): a caller that wants *all* entries of a large book must page; there is no streaming/cursor API. For 200+ entry books this is many round trips, which is acceptable for an in-page local read (no network) but worth watching.

## Verification

- `npm test`: **241 tests pass** (240 before; the entries tests were rewritten for the page object and a new paging/search test was added: 12 entries, two pages, content and key search, offset past the end, negative offset rejection).
- `npm run verify:browser`: **153/153 checks pass**. New: the manager pages a twelve-entry scratch book (8 + 4, ranges `1–8 / 12` and `9–12 / 12`), searches `probe entry 1` and reports `3 条`, then selects and saves an entry with the success status visible.
- Scratch data: the manager probe creates and deletes its own book; no `__loom*` leftovers.

## Risks / outstanding

- The page object is a breaking output change; any out-of-repo consumer must read `data.entries`. This is the first breaking capability change in the project and is called out here and in the API index.
- Search scans the mapped page set in memory per call; a book with tens of thousands of entries would make each search linear. Acceptable for local reads, not indexed.
- The manager caches a whole book on first selection (for full content); a very large book still loads fully at that point. A `worlds.entry.get` capability would avoid it, but is out of scope here.
- `hasMore` is page-relative by design; a caller that mutates the book between pages can see shifted windows (no revision token yet).
