# CHG-20261119-005

- Date: 2026-11-19 (Asia/Shanghai)
- Type: FEATURE, API, TEST, DOCS
- Requirement / motivation: Implement the UI requirements' core capability: a generic, script-driven interface system that can create, compose, update and destroy interfaces at runtime instead of a single hard-coded panel.
- Changes:
  - Added `Loom UI/components.js`: extension-owned component registry with props/events descriptors, type and required checks, default resolution, defensive descriptor copies, duplicate detection, and automatic removal when the owner extension unregisters.
  - Added `Loom UI/builtin-components.js`: 12 built-in components (`text`, `button`, `input`, `toggle`, `select`, `card`, `row`, `column`, `grid`, `divider`, `list`, `badge`). Text is always assigned through `textContent`; props never become HTML.
  - Added `Loom UI/view-tree.js`: pure node normalization, validation, description, path lookup, prop/child mutation and event dispatch, testable without a DOM.
  - Added `Loom UI/views.js`: DOM view engine with `createView`, `getView`, `listViews`, `destroyAllViews`; view handles support `setRoot`, `setProps`, `setChildren`, `appendChild`, `remove`, `describe`, `destroy`. Views are extension-owned and torn down through Core cleanup.
  - UI entry (`Loom UI/index.js`) now installs built-ins, exposes `globalThis.LoomUI`, registers `ui.components` and `ui.views` capabilities, shows a UI summary row in the panel, and keeps the existing panel/host/event behavior.
  - `LoomUI` accepts both `(component)` / `(options)` for Loom UI itself and `(extensionId, component)` / `(extensionId, options)` for other extensions.
  - Bumped Core/manifest/package version to 0.5.0.
- Direct scope: `Loom UI/components.js`, `Loom UI/builtin-components.js`, `Loom UI/view-tree.js`, `Loom UI/views.js`, `Loom UI/index.js`, `Loom UI/style.css`, `Loom UI/components.test.js`, `Loom UI/view-tree.test.js`, `Loom Core/index.js` (version only), `manifest.json`, `package.json`, governance docs.
- Horizontal impact:
  - SYNC: Loom UI entry must register built-ins before views are created; the panel summary and capabilities depend on the component/view registry.
  - ADAPT: Third-party extensions can now register their own components/views; ids are global, so namespacing is their responsibility.
  - NO-CHANGE: Core registry API, host adapter capabilities/events, and SillyTavern source; the UI system composes on top of existing contracts.
  - CONFIRM: Visual styling beyond SillyTavern theme variables and the absence of a visual editor are accepted initial limits.
- Architecture/API/data: Introduces `globalThis.LoomUI` as a separate public facade (Core's API object is frozen, so UI must not extend it). Components and views are in-memory and page-scoped; no persistence or serialization yet.
- Compatibility/migration: New API; no existing caller depends on it. The built-in component ids are initial and may expand.
- Validation:
  - `npm test`: pass, 30 tests (Core 12, Host 6, UI components 5, UI view-tree 5, manifest 2), including component ownership/cleanup, prop validation, node validation, event isolation, path mutation and description without functions.
  - `node --check` for all UI modules and Core/Host: pass.
  - ST page on port 8100 loaded runtime 0.5.0 with `LoomUI` and 12 built-in components.
  - Browser end-to-end: created a nested card/row/text/badge/button/input view; button click handler fired once; `setProps` updated text; `appendChild` added a divider; `describe()` returned component structure without handlers; `ui.components` returned 12 descriptors; `ui.views` listed the active view; `destroy()` removed the DOM and the view list entry.
  - Panel showed "12 个组件 · 0 个活动视图" and 5 capabilities; no Loom console errors.
- Failed checks and corrections:
  - The first implementation attempted `runtime.ui = ...` on the frozen Core API object. This would throw at runtime; changed to a separate `globalThis.LoomUI` facade.
  - `views.js` initially missed the `resolveProps` import; caught by static review before browser testing.
  - Two view-tree tests failed because the shorthand `text` component was not registered in the pure test setup; the tests now register the built-in text component explicitly. All failures are recorded rather than hidden.
- Risks / outstanding: No reactive data binding, no view serialization/deserialization, no visual editor, no image/media/markdown components, no per-view style overrides, and no permission model for component ids. Rendering re-creates the whole view on each mutation, which is acceptable for small panels but not for large dynamic interfaces.
