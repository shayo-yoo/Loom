# CHG-20261123-045

- Date: 2026-11-23 (Asia/Shanghai)
- Type: FEATURE, API, TEST, DOCS
- Requirement / motivation: the user asked for the foundation of "interactive panels inside the chat that the model does not read" — inventory, level, character panels, choice prompts — and asked Loom to decide between writing its own regex layer and relying on SillyTavern's regex extension.
- Stage: branch `feature/prompt-visibility`, foundation only. The widget/panel feature itself is explicitly out of scope.

## Decision

Three mechanisms were compared against the two requirements ("show to the user" and "hide from the model"):

| Option | Verdict |
|---|---|
| Write a Loom regex engine | **Rejected.** SillyTavern's regex already has exactly the semantics needed (`markdownOnly` applies only at display, `promptOnly` only to the prompt). A second engine would duplicate it with different tie-breaking. |
| Push Loom's rules into SillyTavern's regex list | **Rejected as the primary path.** It clutters the user's regex panel with internals the user did not write, requires the regex extension to stay enabled, breaks if the user edits or deletes the entry, and `getRegexedString` is not exposed by `getContext()` — calling it would mean importing host internals. |
| A Loom-owned block syntax plus a prompt filter on SillyTavern's public mutation events | **Chosen.** Only removes Loom's own markers, needs no user configuration, and does not depend on another extension. |

The jurisdiction split that follows:

- **Loom blocks** — syntax Loom owns, semantics it can guarantee; stripped from the prompt automatically, rendered by a future extension.
- **Arbitrary text hiding** — stays with SillyTavern's regex extension, where the rule is user-written and user-visible. Hiding text the user did not write is a much stronger capability and does not belong behind an implicit hook.

## Changes

### `Loom Core/markers.js` (new, pure)

Block syntax, chosen because the delimiters (U+27E6/U+27E7) do not occur in prose, survive SillyTavern's text handling, and — since they are stripped from the prompt — never give the model a pattern to imitate:

```
⟦loom:widget⟧{"slot":"hud"}⟦/loom⟧   paired: the block owns its payload
⟦loom:hud⟧                          pointer: the payload lives in Loom state
```

- `formatBlock(kind, inner?)`, `parseBlocks(text)`, `hasBlocks`, `stripBlocks(text, { replacement })`, `stripBlocksFromMessage(message)`.
- Parsing walks tokens so multiple blocks, mixed case, unclosed openings and orphan closings are all handled; an unclosed opening is reported as a pointer so its marker is still removed rather than leaked.
- `stripBlocks` accepts a `replacement(kind, inner)` so an extension can keep a compact state summary for the model instead of nothing.
- Pure string handling: no DOM, no host access, shared by the host adapter (strip) and a future UI (render).

### Prompt filter in the host adapter

`CHAT_COMPLETION_PROMPT_READY` (`{ chat }`, chat-completion APIs) and `GENERATE_AFTER_COMBINE_PROMPTS` (`{ prompt }`, text-completion APIs) are public, mutating hooks: a listener rewrites the payload that is about to be sent. The adapter attaches to both, strips Loom blocks from every message/string, and leaves untouched payloads identical (same object identity) so nothing is needlessly copied.

- Attached with the existing bridge lifecycle (`tryEnsureBridge`), removed by its `addCleanup`.
- Failure to attach is logged and never blocks the rest of the adapter.
- `prompt.filterStats` (read, ungated) exposes `{ scanned, stripped }` so the effect is observable without dumping prompt content.

## Direct scope

`Loom Core/markers.js` (new), `Loom Core/markers.test.js` (new), `Loom Host/index.js`, `Loom Host/index.test.js`, `tests/browser/verify.mjs`, docs, version markers.

## Horizontal impact

- SYNC: capability list 28 → 29 (`prompt.filterStats`); the sorted expectation in the adapter test was updated.
- SYNC: the host adapter now imports a Core module (`markers.js`) in addition to the Core entry — the first time it imports shared logic rather than only using the global runtime, which keeps one definition of the block grammar.
- ADAPT: two harness probes were made idempotent (registering `verify-probe` only when absent, and not registering it at all where it was unnecessary) after the new filter probe exposed an ordering assumption in the older `live reads` probe.
- NO-CHANGE: `prompt.set`/`clear`/`list` (injection) — a different mechanism with its own permission; nothing about it reaches into the message text.

## Verification

- `npm test`: **279 tests pass** (+9 marker tests: formatting, parsing, mixed case, unclosed/orphan/nested tokens, stripping with and without a replacement, message-shape preservation, cheap pre-check).
- `npm run verify:browser`: **200/200 checks pass** (three consecutive runs). New: emitting SillyTavern's real prompt events with a synthetic payload rewrites the payload in place — chat-completion `{ chat: [...] }` and text-completion `{ prompt }` both lose their blocks while plain text is untouched; `prompt.filterStats` counts the passes; a block written into a real chat message stays in the stored message (`⟦loom:hud⟧v=1⟦/loom⟧`) but arrives at the model as `hud  tail`.

## Risks / outstanding

- The filter only covers those two events. A future SillyTavern API family that builds a prompt another way would bypass it — worth re-checking on a host upgrade.
- Blocks remain in the message source, so they persist into the chat file and are visible in exports and other clients. That is the price of surviving re-renders; stripping on export is a possible later addition.
- Nothing renders blocks yet: an extension that starts writing them today would leave bare markers visible until a renderer exists. This is foundation, not a user-facing feature.
- Whether a `chat.append`-written system message reaches the model at all is still unverified; the filter handles both cases (strips if present), but the token cost question stays open.
- `stripBlocks` is linear per prompt and runs on every generation; for very long chats this is negligible relative to prompt assembly, but it is not free.
