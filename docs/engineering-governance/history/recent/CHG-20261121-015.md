# CHG-20261121-015

- Date: 2026-11-21 (Asia/Shanghai)
- Type: FEATURE, API, TEST, DOCS, ARCH
- Requirement / motivation: Core requirements §3 (scripts must be able to register interfaces and receive results), §4 (registration must describe provider, identity, dependencies and handle conflicts) and §8 (loading failures, duplicate detection, cleanup, runtime state) all assume an extension is more than an identity plus ad-hoc registrations. Until now an extension was "register yourself, register capabilities, remember to clean up", with no activation lifecycle, no dependency ordering, no way to declare needed permissions up front, and no record of why a load failed. Total requirements §7.8–7.9 (extensions built on Loom, future tooling) also need a declarative entry point.
- Stage: extension loading and manifest, running in parallel with the UI-deepening stream (CHG-20261121-016).

## Design decisions

1. **Loading and activation are separate.** `loadExtension` validates the manifest and registers identity only; nothing of the extension runs. `activateExtension` is the explicit step that checks dependencies, requests declared permissions and runs the hook. This keeps a broken extension from executing code merely by being described, and lets a host show what is installed before anything runs.
2. **Failures are state, not exceptions.** A malformed manifest throws (`TypeError`) because that is a programming error at the call site. An activation failure is recorded on the extension (`state: 'failed'`, `error: { code, message }`) and never thrown at the activator: one broken extension must not abort a boot sequence. Codes: `DEPENDENCY_MISSING` (with `details.missing`), `ACTIVATION_FAILED`, `DEACTIVATION_FAILED`, `PERMISSION_REQUEST_FAILED`.
3. **Dependencies must be satisfied, not merely registered.** A managed dependency must be `active`; `loaded`, `inactive` and `failed` are unmet, so tearing a dependency down leaves dependents blocked rather than running against a dead dependency. `unmanaged` counts as satisfied because those extensions were registered directly by bootstrap code (host adapter, UI) whose setup already ran and which can never become `active` through the loader — requiring `active` would have made every extension depending on the host impossible to activate. A self-dependency is rejected at load.
4. **Declared permissions are requested, never granted.** Activation calls `requestPermission`, which raises the consent prompt built in CHG-20261121-013. A failed request is recorded but does not block activation, because an extension may still do useful work without the permission.
5. **Lazy reconciliation instead of callbacks.** `unregisterExtension` is public and can be called directly, so the loader prunes records whose identity disappeared on the next lifecycle call. No `onUnregister` hook was added to Core, keeping the two modules independent.
6. **No circular import.** `loader.js` receives the Core functions it needs (`createExtensionLoader(core)`) instead of importing `index.js`; `index.js` spreads the loader API onto the frozen `globalThis.Loom`.

## Changes

### Core

- Added `Loom Core/loader.js` with `createExtensionLoader(core)` and the lifecycle API: `loadExtension`, `activateExtension`, `deactivateExtension`, `unloadExtension`, `listExtensionStates`, `getExtensionState`.
- Manifest fields: `id`, `name`, `version?`, `description?`, `author?`, `declaredId?`, `entry?` (informational path), `dependencies?`, `permissions?`, `activate?`, `deactivate?`, `content?`.
- Lifecycle events: `core:extension:loaded`, `core:extension:activated`, `core:extension:failed`, `core:extension:deactivated`, `core:extension:unloaded`.
- `getRuntimeInfo()` gained `activeExtensionCount` and `failedExtensionCount`.
- Unmanaged extensions (registered directly through `registerExtension`, as `loom-host`/`loom-ui` do) are reported with `state: 'unmanaged'` rather than being hidden.

## Direct scope

`Loom Core/loader.js` (new), `Loom Core/loader.test.js` (new), `Loom Core/index.js`, `docs/engineering-governance/{API_INDEX,ARCHITECTURE,CHANGELOG}.md`, plus the shared version bump handled during integration.

## Horizontal impact

- SYNC: `api` in `Loom Core/index.js` now spreads the loader methods; the six functions are also named exports for tests.
- SYNC: `getRuntimeInfo()` grew two fields; `PROJECT_STATE` and the panel's counts were checked for shape assumptions (the panel reads specific fields, so it is unaffected).
- NO-CHANGE: `registerExtension`/`unregisterExtension` semantics; the loader is additive on top.
- NO-CHANGE: `Loom Host/*`; the adapter keeps using `registerExtension` directly and appears as `unmanaged`.
- NO-CHANGE: `Loom UI/*` (owned by the parallel stream at the time of writing).
- CONFIRM: whether unmanaged extensions should be migrated onto the loader. Not done: the host and UI register before the loader is known to be stable, and a migration would change their boot order.

## Validation

- `Loom Core/loader.test.js`: **14 tests pass**. Covers manifest validation (object/id/name/version/entry/hooks/dependencies/permissions/self-dependency), duplicate load, registration on load only, activation running the hook once, dependency gating (missing, deactivated, unknown, unmanaged-bootstrap), activation failure isolation with a healthy neighbour, retry after failure clearing the error, declared permissions producing exactly one consent request and zero grants, deactivation hook failure recorded while still deactivating (and not re-running), unload deactivating then unregistering, `unmanaged` reporting, and the full lifecycle event sequence.
- `npm test`: **140 tests pass** at the integrated 0.14.0 (117 straight after this change; the UI stream added the rest).
- `npm run verify:browser`: the lifecycle probe exercises `loadExtension` → `activateExtension` → panel state → consent request → dependency blocking → unload against a live SillyTavern (65/65 checks in the integrated run).
- Not run: a real extension package loaded from disk. Manifests are JavaScript objects passed in code; file discovery is not implemented.

## Failed checks and corrections (recorded, none hidden)

1. The first loader draft had no reconciliation, so `afterEach(unregisterExtension)` left records behind and the next test failed with "Extension is already loaded". Fixed by pruning records that are no longer registered, plus `unloadExtension` falling through to `unregisterExtension` when no record exists.
2. Two test expectations were wrong, not the code: a repeated `deactivateExtension` still reports the recorded failure (the hook does not re-run), and unloading an active extension emits `deactivated` before `unloaded`. Both expectations were corrected after checking the actual semantics.
3. An event assertion emitted `null` into a handler that reads `payload.id`, producing a listener error. The test now emits a realistic payload.
4. **Tooling incident:** an attempt to insert the reconciliation calls with PowerShell 5.1 `Get-Content -Raw` + `Set-Content` corrupted `loader.js` (UTF-16/ANSI round-trip through a UTF-8 file), which the file editor then refused as invalid UTF-8. The file was rewritten in full and the remaining edits used the editor. Lesson: never edit UTF-8 sources through PowerShell string replacement in this environment.

## Risks / outstanding

- Dependency cycles between two extensions simply leave both `failed` with `DEPENDENCY_MISSING`; there is no cycle-specific diagnosis.
- Dependency versions are not checked — only the extension id. A manifest cannot require "host ≥ 0.13".
- Activation is synchronous; an extension whose activation needs async work must manage that itself (the hook's promise is not awaited).
- Deactivation does not unregister capabilities, so a deactivated extension's capabilities remain callable until unloaded. This is deliberate but means "inactive" is a lifecycle label, not a sandbox.
- Loader state is in memory: on reload every extension starts `loaded` and must be activated again by whatever boots it.
- No manifest file discovery: a manifest is a JavaScript object passed in code. Reading manifests from disk/URLs is a host concern and not implemented.
