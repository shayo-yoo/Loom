# CHG-20261121-024

- Date: 2026-11-21 (Asia/Shanghai)
- Type: FEATURE, API, FIX, DATA, TEST, DOCS
- Requirement / motivation: With create/delete (CHG-20261121-023) the world book had a whole-book lifecycle but no way to move data in or out, so backup, duplication and migration were impossible; rename was explicitly left open because it needs reference handling. Total requirements §7 (host interaction) and the project's own "extensions must not reach into SillyTavern internals" rule both point at providing these through declared capabilities.
- Stage: self-planned goal `goal-5f50eed7`, increments 1–3 (export, import, rename) executed in one pass because they share the same write path.

## Changes

### `worlds.export` (read)

`{ name }` → `{ name, entries, data }`. Returns the host's **raw book object** (detached copy) rather than the mapped subset `worlds.entries` exposes, because import must round-trip fields Loom does not model (`displayIndex`, `automationId`, …). Ungated, consistent with `worlds.entries`: the sensitive part (entry text) is already readable there, and export adds structure, not new content.

### `worlds.import` (write, `host.worldinfo.manage`)

`{ name, data }` → `{ name, entries, created }`. Refuses an existing name (`WORLD_EXISTS`) — import can never overwrite. Payload validation happens before any request: `entries` must be an object, each entry an object, no reserved uid (`__proto__`/`prototype`/`constructor`), at most 5000 entries and 5 MB of JSON. Validated payloads are re-serialised through `JSON.parse(JSON.stringify(...))`, so what reaches the host is plain JSON with no prototypes.

### `worlds.rename` (write, `host.worldinfo.manage`)

`{ name, to, confirm }` → `{ from, to, migrated }`. `confirm` must echo the current name (`CONFIRMATION_REQUIRED`); `to` must differ case-insensitively (`INVALID_INPUT`); `to` must be free (`WORLD_EXISTS`).

- **Character-card bindings refuse the rename.** SillyTavern's own rename also rewrites character lore links, which means writing character cards — something the adapter cannot do. A book bound to a card fails with `WORLD_IN_USE` and `details.characters`, before any write, instead of renaming and silently unbinding it.
- **References it can migrate are migrated**: the current chat's `chat_metadata.world_info` and `power_user.persona_description_lorebook`. `migrated` reports exactly what changed.
- **A globally activated book is refused** (`WORLD_IN_USE`, `details.selection`). The first implementation tried to retarget the `#world_info` dropdown; the browser probe showed the host rebuilds that element during `updateWorldInfoList` and does not guarantee the renamed option exists, so the migration could silently leave nothing selected. Refusing and telling the user to deactivate first is the predictable behaviour; the adapter never mutates the host's activation dropdown.
- Copy-then-delete ordering: the new book is written and verified first; only then is the old name removed. A failure leaves the original intact (possibly plus a copy, which is reported).

### Fix: the host's world cache was not updated

`worlds.create`/`import`/`rename` originally posted to `/api/worldinfo/edit`, which writes the file but leaves SillyTavern's in-memory `worldInfoCache` untouched. Consequence found by the harness: delete a book, recreate it under the same name, and `worlds.entries` still returned the **previous** entries. Writes now go through `context.saveWorldInfo(name, data, true)` when the host exposes it (it updates cache and file), falling back to the endpoint only when it does not.

- SYNC: host capability list (17 → 20); permission assertions cover the two new `manage` capabilities and assert `worlds.export` is ungated.
- SYNC: the world-write browser probe now recreates a book after deletion and asserts it starts empty — the regression test for the cache bug.

- CONFIRM: whether rename should update character cards once card writing exists. Not done, and the refusal is the honest interim behaviour.

## Validation

- `npm test`: **203 tests pass** (191 before; +12: export fidelity and detachment, export errors, import round-trip, import permission/overwrite, payload validation incl. hostile `__proto__` and oversized books, empty import + ghost book, rename migration, rename refusal on card binding, rename refusal on global activation, rename validation matrix, rename permission, host-writer preference).
- `npm run verify:browser`: **107/107 checks pass**. New: a real export → import round-trip preserves content/keys/order; a globally activated book is refused before any write; a real rename moves chat + persona bindings, keeps the entry, and drops the old name; a deleted-then-recreated book is empty (the cache regression); all scratch books are removed afterwards.
- The hostile `__proto__` case is built with `JSON.parse` in the test because an object literal would set the prototype instead of creating the key — recorded so the test is not "fixed" later into passing for the wrong reason.

## Failed checks and corrections (recorded, none hidden)

1. The capability-list and permission assertions failed after adding three capabilities — updated to the contract.
2. A payload-validation case used an object literal with `__proto__`, which does not create an own key, so the guard did not trigger and the test wrongly failed. Rewritten with `JSON.parse`.
3. A test captured `originalFetch` after the stub had already replaced it (`ReferenceError`/restore ordering) and was restructured.
4. The browser rename probe initially reused the export probe's scratch names and read a leftover entry, which produced a false failure — and then exposed the **real** cache bug. The probe now uses dedicated names *and* asserts recreate-is-empty; the underlying defect was fixed in the adapter rather than by isolating the names.
5. Selection handling went through three iterations: migrate with a captured handle (stale after the host rebuilds the dropdown), migrate with a re-query (still found no option for the renamed book), then refuse. Each step was driven by a failing browser assertion, and the final behaviour is the one the goal's objective asked for. The adapter no longer touches the host's activation dropdown at all.

## Risks / outstanding

- `worlds.remove` still cannot evict the host cache (SillyTavern exposes no delete function), so after a delete, `worlds.entries`/`worlds.export` on that name can keep returning cached data until reload. Creating a book under that name overwrites the cache entry, which is why the recreate case is correct; the read-after-delete case remains stale and is documented.
- Rename refuses when a character card is bound or the book is globally activated; card links would need card writing, and the activation dropdown is the host's to manage.
- Rename does not migrate references outside chat metadata and the persona lorebook (for example chat-search text or third-party extension state).
- Import is a single-shot copy: no merge, no append into an existing book, no entry-level conflict resolution.
- Exported data carries every host field, including ones Loom does not understand; a future host version may add fields that import forwards verbatim (intended) or fields that change shape (unverified).
