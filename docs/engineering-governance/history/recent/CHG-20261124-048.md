# CHG-20261124-048

- Date: 2026-11-24 (Asia/Shanghai)
- Type: FIX, FEATURE, TEST, DOCS
- Requirement / motivation: the user reported that the character-panel demo "did not take effect, or took effect but was not visible, cause unknown". Investigating found three independent defects plus two harness problems.
- Stage: branch `feature/character-panel-demo` (continuation), version 0.40.0.

## Why nothing showed (root causes, in order of impact)

1. **Nothing ever wrote the marker.** Block rendering only finds markers in message text, and the extension deliberately never wrote one: it exposed the marker as a read-only capability (`panel.block`) and nothing consumed it. A fresh chat therefore had no panel at all. Fixed by `panel.show`, which appends exactly one panel message, plus a wand-menu entry (`mountToSlot(id, 'menu', …)`) so the action is discoverable. Insertion stays explicit: writing into a conversation is a visible side effect.
2. **A rendered panel could disappear on the next refresh.** `refreshBlocks` treated "marker missing" as "block removed" and disposed the message's mounts — but rendering *replaces* the marker, so the second refresh destroyed the widget it had just built. Now the absence only disposes when there is no `.loom-block` in the body.
3. **An edited extension kept running old code.** Browsers cache ES modules per URL, and the entry URL never changed, so a fixed `index.js` could still run the previous module. Package imports are now cache-busted with the index's `contentHash` (`?v=…`); the index already owned that fingerprint.
4. **A stale write loop.** An earlier iteration appended the panel per host event and left eight identical messages in the user's chat file. Activation now only *draws an existing* marker; `host:chat:changed` and `core:permission:resolved` re-draw but never append.
5. **Grants arriving late.** The panel needs `host.chat.write` in addition to the two it declared. `togglePanel` requests it when a refusal is a permission error, so the consent prompt appears instead of nothing.

Also fixed while validating: `panel.show` declared an output schema without `index` and returned it, so a successful append was reported as `INVALID_OUTPUT`.

## Design decisions

- **Marker helpers became pure functions** (`panelMarkerFor`, `hasPanelMarker` in `state.js`) so the "does this chat already have a panel" decision is unit-testable without a browser. `index.js` keeps only the host interaction.
- The panel is a **pointer block** (`⟦loom:character.panel⟧⟦/loom⟧`, no payload): all content comes from Loom state, so the message text carries no data and the prompt filter strips it entirely.

## Harness problems found and fixed

- The panel probe originally needed an open chat, so it created a scratch character, selected it, and deleted it at the end. Deleting the *selected* character leaves SillyTavern on its safety screen, and every later probe that needs a selection then hangs on `selectCharacterById` (two runs stalled for >10 minutes). Restoring the previous selection also hung. The probe now avoids chat writes completely: it renders into a synthetic `.mes`, drives `panel.apply`/receipts over the in-memory conversation, and asserts the capability surface. The append path is unit-tested where it can be (`hasPanelMarker`) and verified by hand — recorded as a known gap rather than faked.
- Receipt handling was blocked by *persisted* `processedMessages` indexes from earlier chats, so a fresh receipt was ignored. The probe now emits `CHAT_CHANGED` first to reset the scope, which is also the documented behaviour for scripts.
- Leftover artifacts from the crashed runs (`__loom_verify_*` worlds, cards, chat directories) made the world-book-manager probe fail with `WORLD_EXISTS` and stale pagination; they were removed manually. They were leftovers of the harness, not of user data.

## Verification

- `npm test`: **300 tests pass** (+1 marker-helper test: marker format, kind validation, and that another kind does not count).
- `npm run verify:browser`: **215/215 checks pass**, three consecutive runs. The panel probe covers: reset to a known state, marker capability, rendering into a synthetic message (level/gold/empty bag, marker gone), `panel.apply` re-rendering the mounted widget to `药水 ×2`, injection carrying state + receipt rules + change line, an assistant receipt changing items/gold/level exactly once, post-receipt injection, and the full capability/block surface.
- Manual check in a real chat: the wand-menu entry inserts the panel, it renders immediately, and a data change updates it in place.

## Known gaps

- The `panel.show` append path is not covered by the browser harness (reason above). Simulating it safely would need a second disposable chat that the harness can delete without touching the selected character.
- Alignment between Loom and SillyTavern on *which* chat is open is a real risk class: an append writes to the open chat, so the entry point must stay explicit.
- The user's test chat contains one panel message written during diagnosis; it now renders correctly and can be deleted as a normal message.
- `chats/测试/*.loom-backup.jsonl` exists in the profile; no Loom code writes that name, so it belongs to other tooling and was left untouched.
