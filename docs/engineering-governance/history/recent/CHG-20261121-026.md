## Changes

### `chat.edit` (write, `host.chat.write`)

`{ index, text }` 鈫?`{ index, previous, saved, rendered }`.

- Mutates the message at `index` through the data model, then calls the host's `updateMessageBlock(index, message)` so the rendered element and the data stay in step; a raw `chat[index].mes = text` would leave the DOM showing the old text.
- **`previous` is the undo token.** The old text is returned before the write, so a caller can restore it with a second `chat.edit`.
- **Rollback:** if `updateMessageBlock` throws, the message is restored from the pre-write snapshot and the call fails with `MESSAGE_UPDATE_FAILED`; a failed edit never leaves a half-written message.
- `saved`/`rendered` report what actually happened. A host whose `saveChat` rejects leaves the text in memory and reports `saved: false` 鈥?the caller can see that a reload would lose the edit.
- Out-of-range index fails with `MESSAGE_NOT_FOUND` and `details.length`; no chat open fails with `NO_CHAT`.

### `chat.delete` (write, `host.chat.write`)

`{ index, expect }` 鈫?`{ index, removed, remaining }`.

- **`expect` must repeat the current message text exactly** (`CONFIRMATION_REQUIRED`, with `details.current`). Deletion is irreversible and index-based, so a stale index must not be able to destroy an unrelated message.
- Delegates to the host's `deleteMessage(index, undefined, false, true)`: swipe/tool-call cascade, prompt-item cleanup and the debounced save all belong to SillyTavern; reimplementing them with `chat.splice` would silently diverge. The host confirmation dialog is suppressed (`askConfirmation: false`) because consent is Loom's permission gate plus the `expect` echo, and a dialog cannot be driven from a capability.
- `removed` is measured (`lengthBefore - lengthAfter`), not assumed: a tool-call cascade can remove more than one entry. A host that removes nothing fails with `MESSAGE_DELETE_FAILED`.

## Horizontal impact

- SYNC: host capability list (21 鈫?23); write-capability table and the chat section in `API_INDEX.md` gain both rows.
- ADAPT: the browser probe creates a scratch character, selects it, edits its greeting, asserts the **chat file on disk** contains the edited text, deletes it, asserts the file no longer contains it, and removes the scratch card with its chat. The user's chats are never opened.
- NO-CHANGE: `chat.append` semantics (still a system-message writer; still rolls back on a failed render), `chat.messages` reads.
- **Known limitation carried over:** appending a system message still fails in an environment without a selected persona (`Cannot read properties of undefined (reading 'is_user')`); that is the host's rendering path, documented in CHG-20261121-022. Editing and deleting do not need a persona, so the destructive path is verified independently of it.
