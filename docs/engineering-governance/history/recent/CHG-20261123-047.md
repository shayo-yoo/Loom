## The sample: `extensions/character-panel/`

A complete, runnable loop, split so the rules are testable without a browser:

- `state.js` (pure): `normalizeState`, `applyCommand` (item/gold/exp/level), `applyReceipts`, `parseReceipts`, `describeState`, `panelLines`. Level-up is a loop (`exp ≥ expNext` → level, `expNext = round(expNext × 1.5)`), so one receipt can cross several levels; gold and counts floor at zero and empty item entries disappear.
- `index.js` (glue): registers a block kind `character.panel`, three capabilities (`panel.get`, `panel.apply`, `panel.reset`, plus `panel.block` for the marker), a `prompt.set` writer, and a `host:message:received` handler that applies receipts.

**Panel** — `registerBlock` renders a card with level/exp/gold and one "用 X" button per item; a click goes through the same `applyCommand` as receipts, so the UI and the model cannot diverge.

**Injection** — `describeState` compiles state + the receipt rules into:

```
【角色状态】Lv.2｜经验 50/225｜金币 15｜背包：火把×1、药水×2
【回执规则】需要改变角色状态时，在回复末尾追加一行（可多行）：[[item:物品名:+1]] … [[gold:+10]] … [[exp:+50]] … [[level:+1]] …
【最近变化】获得 火把 ×1（现 1）
```

Injected with `prompt.set` under key `status` at depth 1, so the model sees the current numbers **and** how to change them.

**Receipts** — `[[gold:+10]]`, `[[exp:+50]]`, `[[level:+1]]`, `[[item:药水:+2]]`. Parsed from the **stored message text**, not the DOM (the block renderer replaces the marker in the body), applied once per message index, with invalid commands surfaced rather than swallowed.

## Problems found and fixed while validating

1. **A rendered block could never be refreshed.** Rendering replaces the marker with the widget container, so `refreshBlocks` (which looks for markers in text) found nothing after the first render — the panel kept showing `金币 10` after the state changed. Added `LoomUI.rerenderBlocks(extensionId?)`, which walks live mounts and re-runs each builder in place. The sample now uses it.
2. **`minimum`/`maximum` were validated with the length rules**, so `{ minimum: -9999 }` was rejected and any signed-delta capability could not even be registered — the sample's `panel.apply` was silently missing (the registration error was swallowed by a catch). Core now allows negative numeric bounds and requires non-negative **integers** only for `minLength`/`maxLength`/`minItems`/`maxItems`. Regression test included.
3. **Receipts were applied to history after reload.** State is persisted, so replaying would double-apply. The sample seeds every existing message index as processed at activation, and re-seeds on `host:chat:changed`.
4. **A missing grant failed silently.** Without `host.chat.read` the handler simply found no messages; it now logs the cause once.

## Risks / outstanding

- Receipts stay in the assistant's message text, so they are part of the conversation and reach the model again (a few tokens, and a readable log). Making them invisible would require hiding the syntax from the model, which would also make it unlearnable.
- The panel is read-mostly: only "use one item" is interactive, and clicking inside a message still competes with SillyTavern's own handlers.
- `panel.apply` swallows a registration failure with `try { … } catch {}`: that is what hid bug 2. It is now a deliberate "already registered on reload" guard, but the class of silent failure is worth revisiting.
- The sample stores `processedMessages` capped at the last 500 indexes; a very long session could re-process a message older than that.
- Injection depth is fixed at 1; there is no UI to configure it.
