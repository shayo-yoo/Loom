# CHG-20261121-023

- Date: 2026-11-21 (Asia/Shanghai)
- Type: FEATURE, API, DATA, TEST, DOCS
- Requirement / motivation: CHG-20261121-014 recorded "no world-book create/delete/rename" and explained why deletion was deferred: it is destructive and needs an explicit confirmation surface. That left the whole-book lifecycle open — an extension could fill a book but never make one, and users had to delete books by hand. Total requirements §7 (host interaction) and Core requirements §5 (declared, bounded writes) both point at finishing it.
- Stage: self-planned goal `goal-dbba54ec`, increment 3 (destructive write-back), after message writes.

## Design decisions

1. **Separate permission, not a stronger entry permission.** `worlds.create`/`worlds.remove` require `host.worldinfo.manage`; `host.worldinfo.write` (entry edits) is not enough. Granting "edit a lore entry" must never imply "delete the book".
2. **Removal requires the name echoed back.** The caller must pass `confirm` equal to `name`; a mismatch fails with `CONFIRMATION_REQUIRED` and makes no request. This turns the common accident (a wrong variable, an `undefined` name) into a typed error instead of a deletion, and it is a second gate on top of the consent prompt.
3. **Creation refuses to overwrite.** An existing name fails with `WORLD_EXISTS` before any request, so a misconfigured extension cannot clobber a book by "creating" it.
4. **The adapter calls SillyTavern's own endpoints.** `getContext()` exposes no create/delete function; SillyTavern itself uses `POST /api/worldinfo/edit` and `POST /api/worldinfo/delete` with `getRequestHeaders()`. This is a deliberate, documented exception to "use `getContext()` only" — the alternative (importing host internals) couples worse, and reimplementing file I/O is out of scope.
5. **Verify the effect, do not trust the call.** After each operation the adapter refreshes the world list (`updateWorldInfoList`) and checks membership: a create that the host did not register is `WORLD_CREATE_FAILED`, a delete that left the book listed is `WORLD_REMOVE_FAILED`.
6. **No silent rollback for deletion.** Unlike `chat.append`, a failed delete cannot be undone by restoring the book; the capability reports which state it ended in rather than pretending.

## Changes

### Host (`Loom Host/index.js`, 0.20.0 → 0.21.0)

- `worlds.create`: `{ name }` → `{ name, created }`. `WORLD_EXISTS`, `WORLD_CREATE_FAILED`, `HOST_UNSUPPORTED`.
- `worlds.remove`: `{ name, confirm }` → `{ name, removed }`. `CONFIRMATION_REQUIRED`, `WORLD_NOT_FOUND`, `WORLD_REMOVE_FAILED`, `HOST_UNSUPPORTED`.
- Both gated by `host.worldinfo.manage` and both refresh the host's world list before reporting.

## Direct scope

`Loom Host/index.js`, `Loom Host/index.test.js`, `tests/browser/verify.mjs`, version markers, docs.

## Horizontal impact

- SYNC: host capability list (15 → 17); permission assertions now cover `host.worldinfo.manage`.
- SYNC: the browser world-write probe now creates the scratch book **through Loom** instead of raw `fetch`, and deletes it through `worlds.remove`, so the whole lifecycle is verified end to end. The raw-fetch helpers remain only as cleanup safety nets.
- NO-CHANGE: `worlds.entries` and entry CRUD contracts; `worlds.entry.create` still requires the book to be in the host's list, which is now satisfiable through `worlds.create`.
- NO-CHANGE: the panel derives capabilities and permissions from the registry, so both new entries and the new permission appear without UI edits.
- CONFIRM: whether a dedicated UI confirmation dialog (rather than a consent prompt plus `confirm`) is required before a destructed delete is considered safe. Recorded as a product question, not silently answered.

## Failed checks and corrections (recorded, none hidden)

1. The capability-list assertion and the permission assertion failed after adding the capabilities — updated to the new contract.
2. The first stub for the world-book endpoints omitted `loadWorldInfo`, so `worlds.create` correctly refused with `HOST_UNSUPPORTED` while the test expected success. The stub was wrong, not the guard.
3. A test for the missing-`fetch` path deleted `globalThis.fetch` and then installed a stub that re-added it, so the call succeeded and the assertion read `error` of a success. Restructured to keep `fetch` absent for that call.

## Risks / outstanding

- A delete is irreversible; the only protections are the separate permission, the consent prompt and the `confirm` echo. There is no soft-delete, backup or undo.
- Confirmation is API-level, not a user dialog: an extension that has been granted `host.worldinfo.manage` can delete any book it names.
- `worlds.create` creates an empty book; it cannot seed entries in one call (entry creation is a separate, cheaper permission that the caller must also hold).
- Rename is still missing; it needs both create and remove semantics plus link rewriting.
- Endpoint coupling: a SillyTavern release that moves `/api/worldinfo/{edit,delete}` breaks creation and deletion (reads use `getContext()` and are unaffected). Recorded as an accepted adapter-level risk.
