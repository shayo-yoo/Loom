# CHG-20261121-022

- Date: 2026-11-21 (Asia/Shanghai)
- Type: FEATURE, API, UI, TEST, DOCS
- Requirement / motivation: After read coverage (CHG-20261121-010) and world-book entry writes (CHG-20261121-011/014), the framework could not put anything *into* a conversation, which blocks narration tools, story directors and any extension that reports state to the reader. The total requirements §7 name chat automation as a first-class use case, and Core requirements §5 require read and write capabilities to be declared separately.
- Stage: self-planned goal `goal-dbba54ec`, increment 2 (write-back), after state persistence because a write path should be able to remember what it wrote.

## Design decisions

1. **Use the host's own writer.** The capability maps onto SillyTavern's `sendSystemMessage`, the only stable function the host exposes for appending a message. Fabricating a chat entry would bypass its rendering, bookkeeping and events — exactly the "adapter must not reimplement host internals" rule.
2. **System messages only, with an allowlist.** `narrator` (default), `comment`, `generic`. User and character messages need a generation lifecycle that Loom does not own, and an allowlist keeps a typo from silently pushing `undefined` into the chat (which the host would then fail to render).
3. **A closed chat is an error, not a silent no-op.** `NO_CHAT` when there is no chat id and the chat is empty; writing into a non-existent conversation would lose the message.
4. **Render does not imply persisted.** `sendSystemMessage` renders but never saves, so the handler calls `saveChat?.()` and treats a message that is not saved as not written.
5. **Rollback on any failure.** The host pushes before rendering, so a render throw leaves a half-written entry; the handler pops everything it added before reporting, and a failed append leaves the chat byte-identical.

## Changes

### Host (`Loom Host/index.js`, 0.19.0 → 0.20.0)

- Added `chat.append` with input `{ text, type? }` and output `{ appended, type, index }`, gated behind **`host.chat.write`**.
- `CHAT_MESSAGE_TYPES` allowlist and a 4000-character text limit, both enforced by the input schema.
- New error codes surfaced through the capability: `NO_CHAT`, `HOST_UNSUPPORTED` (unknown type, host without `sendSystemMessage`, or a host-side render failure), plus the existing `PERMISSION_DENIED` from Core.

## Validation

- `npm test`: **186 tests pass** (180 before; +6: append + save, permission gate, no-chat, invalid type/oversized text, rollback of a corrupt entry, unsupported host).
- `npm run verify:browser`: **91/91 checks pass**. The probe confirms the gate (`PERMISSION_DENIED` without `host.chat.write`), that the host exposes a writer, and that a failed append leaves the chat length unchanged.
- **Real write path is not exercised by the harness, and says so.** The headless session's chat already contained 5 entries, one of them malformed; SillyTavern's own renderer then threw `Cannot read properties of undefined (reading 'is_user')`. A separate one-off diagnostic proved `sendSystemMessage('generic', …)` succeeds on a clean chat (0 → 1 message with the expected shape), so the failure is a host-side hazard on a dirty chat, not a capability defect. The harness records this as `chat.append real write path — not exercised` instead of claiming success.

## Failed checks and corrections (recorded, none hidden)

1. `chatAppendCapability` was declared after `CAPABILITIES`, so the module crashed at import (`Cannot access before initialization`). Moved above the array.
2. The test helper used `options.chatId ?? 'chat-1'`, which turned an explicit `null` into the default and made the `NO_CHAT` test pass a real id. Switched to `Object.hasOwn`.
3. The first handler had no `try/catch` around `sendSystemMessage`; when the host threw mid-render, the half-written entry stayed in the chat. The failure was reproduced in the browser run and fixed with an unconditional rollback.
4. The state-persistence probe asserted "namespace disappears" without clearing a namespace seeded by a previous run, so it failed spuriously once; the probe now clears its own namespace first.

## Risks / outstanding

- Only system-message types are writable. Narration is covered; speaking *as* the user or character is not.
- The host can fail to render into a chat that already contains a malformed entry; Loom detects and reports it but cannot repair the chat.
- A successful append changes `chat` and is saved immediately; there is no batch or transactional write, so several appends are several saves.
- Nothing notifies extensions of their own write; consumers should subscribe to host events or re-read `chat.messages`.
- The real success branch is verified by a manual one-off diagnostic, not by the standing harness — the harness would need a clean, disposable chat to do it safely.
