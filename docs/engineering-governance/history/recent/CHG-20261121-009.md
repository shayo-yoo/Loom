# CHG-20261121-009

- Date: 2026-11-21 (Asia/Shanghai)
- Type: FEATURE, API, DATA, TEST, DOCS
- Requirement / motivation: CHG-20261120-008 shipped the permission model but recorded a blocking limitation: grants lived only in memory, so every reload cleared consent and `settings.set` became unusable again. A permission model that forgets every decision on refresh does not satisfy "Core 应保留不可被普通扩展绕过的基础访问约束" in practice (Core requirements §8) and forces the user to re-authorise after each page load. This change persists the grant table.
- Supersedes the "grants are session-scoped" limitation recorded in CHG-20261120-008.

## Changes

### Core (`Loom Core/index.js`, runtime 0.8.0 → 0.9.0)

- Added `setPermissionStore(store | null)`. The store contract is `{ load(): snapshot, save(grants): void }`; Core keeps owning the grant table and the adapter only decides where the snapshot lives, so no storage dependency enters Core.
- On attach, the snapshot is normalised and applied: grants for already-registered extensions apply immediately, the rest are held in `pendingGrants` and applied when that extension registers. This makes install order irrelevant (the host can install the store before or after other extensions load).
- Malformed snapshot entries are dropped instead of throwing: a corrupted settings file must not stop the runtime from booting. `load`/`save` failures are reported through `console.warn` and never break the in-memory table.
- The snapshot is written on `grantPermission`, `revokePermission` and `unregisterExtension` (so a removal is persisted, not just forgotten).
- `getRuntimeInfo()` gained `permissionStoreAttached`.

### Host (`Loom Host/index.js`, 0.8.0 → 0.9.0)

- Installs a permission store backed by persisted SillyTavern settings: the snapshot lives at `extensionSettings.__loom.grants` and every write flushes with `saveSettingsDebounced()`.
- The reserved root is `__loom` because extension ids must start with a letter or digit, so a leading underscore can never collide with a caller-scoped settings namespace (`extensionSettings[callerId]`).
- A missing host is treated as "nothing persisted yet": `load` returns an empty table and `save` is a no-op, instead of throwing on every boot outside SillyTavern. Genuine write failures still throw and are reported by Core.
- The store stays attached for the page lifetime rather than detaching in a cleanup hook: unregistering an extension must still be able to persist the removal, and a detached store would leave a stale grant in storage.

## Direct scope

`Loom Core/index.js`, `Loom Core/index.test.js`, `Loom Host/index.js`, `Loom Host/index.test.js`, `manifest.json`, `package.json`, `docs/engineering-governance/{API_INDEX,ARCHITECTURE,PROJECT_STATE,CHANGELOG}.md`.

## Horizontal impact

- SYNC: version markers — Core `LOOM_VERSION`, Host `HOST_VERSION` (tracks the runtime), `manifest.json`, `package.json`. The UI derives its version from the runtime, so it needed no change.
- ADAPT: host tests that asserted `extensionSettings` was untouched now account for the `__loom` root appearing once a grant is made; the non-serializable-value test measures the save count as a delta instead of an absolute, because granting itself saves.
- ADAPT: host `afterEach` unregisters before deleting the `SillyTavern` stub, so the removal flush does not run against a missing host.
- NO-CHANGE: `Loom UI/*` — grants persist without UI involvement; the panel keeps reading `listPermissions()` and reflects restored grants on first render.
- NO-CHANGE: `settings.*` capabilities and their permission gating; the reserved root is deliberately separate from caller namespaces.
- CONFIRM: whether Core state should also be persisted. Deliberately not done here: state values have no versioning story, and making them durable by default would resurrect stale shapes after an extension update.

## Architecture / API / data

- New public API: `setPermissionStore` (additive, optional). Without a store nothing changes.
- Data ownership: storage stays in the host adapter; Core only defines the snapshot shape `[{ extensionId, permissions: string[] }]`.
- New persisted key: `extensionSettings.__loom.grants` (array). No migration needed; absence is treated as an empty table.
- Runtime info gained `permissionStoreAttached`.

## Compatibility / migration

Additive. A pre-existing `__loom` key would be adopted as-is; if its shape is wrong it is normalised away rather than crashing. Grants that existed only in memory before this change cannot be recovered — the user re-grants once, and it then persists.

## Validation

- `npm test`: **pass, 73 tests** (was 69). New coverage: malformed store rejection and detach; restore for registered and later-registered extensions with malformed snapshot entries dropped; snapshot writes on grant/revoke/unregister (4 saves asserted); a throwing store still allows grants and reports both failures; host persistence into `__loom` and restore-on-boot.
- `node --check` on `Loom Core/index.js`, `Loom Host/index.js`: pass (re-run after the version bump).
- Not run: browser verification of 0.9.0. Persistence was verified against a stubbed SillyTavern context, not against a live `settings.json` write in Chrome. Recorded as outstanding.

## Failed checks and corrections (recorded, none hidden)

1. First host-store draft used `extensionSettings()` inside `load`, which threw on every boot without a host and printed a warning during test re-imports. Changed to "missing host means empty table".
2. First draft of the host tests kept `delete globalThis.SillyTavern` before unregistering, so the removal flush warned against a missing host. Order corrected.
3. The non-serializable-value test asserted an absolute save count; granting now saves too, so it measures a delta.
4. A Core test called `checkPermission('valid-but-bad-perm', 'bad perm')`, which throws by design on an invalid permission name. The test now registers the extension and asserts its grant list is empty.
5. Initially considered detaching the store in a host cleanup hook. Rejected: `unregisterExtension` persists the removal *after* cleanups run, so detaching first would leave stale grants in storage.

## Risks / outstanding

- Consent is still manual (open the panel, toggle). There is no "extension requests a permission" flow, so a user who does not know the panel exists sees `PERMISSION_DENIED` and no prompt. This is the next UX gap.
- Persisted grants are keyed by the Loom extension id. Renaming an extension silently loses its grants (they remain in storage as an orphan entry until overwritten).
- `__loom` is a reserved key in SillyTavern's flat `extensionSettings`. Nothing enforces the reservation; a third-party ST extension using the same key would collide.
- The store is synchronous. That is fine for SillyTavern settings (in-memory plus debounced save) but a future async backend would need an async contract.
- Browser verification of 0.9.0 is outstanding.
