# CHG-20261121-013

- Date: 2026-11-21 (Asia/Shanghai)
- Type: FEATURE, API, UI, TEST, DOCS
- Requirement / motivation: After CHG-20261121-012 the permission model was enforced and persisted but still silent: an extension that lacked a grant received `PERMISSION_DENIED` and the user had to know the panel existed and find the right toggle. The shared interface agreement §7 requires understandable error feedback rather than a console line, and the Core requirements §8 require basic runtime state management around access constraints. This change turns a refusal into an explicit, visible question.
- Stage: permission request flow (the next step agreed after CHG-20261121-012).

## Changes

### Core (`Loom Core/index.js`, 0.11.1 → 0.12.0)

- `requestPermission(extensionId, permission, { reason? })` opens a consent request and emits `core:permission:requested`. Requesting **never** grants anything. Already-held permissions resolve immediately (`status: 'granted'`, no prompt); a repeated request for the same extension+permission reuses the open prompt instead of stacking them.
- `listPermissionRequests()` returns the open queue sorted by extension then permission.
- `resolvePermissionRequest(requestId, { approved })` grants through the same path as `grantPermission` (so the decision is persisted by the store) or denies and leaves the permission unheld. A stale id returns `status: 'unknown'` rather than throwing, because a UI can race another consent surface. Emits `core:permission:resolved`.
- Unregistering an extension drops its open prompts, and approving a request whose extension disappeared meanwhile resolves as `denied` instead of granting to nobody.
- `getRuntimeInfo()` gained `permissionRequestCount`.

### UI (`Loom UI/`)

- Added `consent.js` (pure): `summarizeRequests` joins requests with extension display names and the capabilities that declare each permission; `buildConsentNodes` produces a declarative node tree with per-request approve/deny buttons.
- The prompt is mounted in `#loom_consent` through **`LoomUI.createView`** — the framework's view engine is now a real consumer of its own UI system instead of only hand-written markup. The prompt holds no state: it is re-rendered from Core on every request/resolution and disappears when the queue is empty.
- Approve/deny re-render the permission section and the settings drawer, and a resolution event from anywhere refreshes them too.
- Fixed a real toggle bug: `togglePermission` decided the direction from the rendered `data-granted` attribute, which goes stale when a grant changes elsewhere (for example through the consent prompt). It now asks Core (`checkPermission`) at click time. The browser harness caught this as a non-deterministic run before it could reach a user.
- Style: fixed bottom-right panel on desktop, full width on narrow screens, safe-area aware, themed with the host's CSS variables.

## Horizontal impact

- SYNC: version markers → 0.12.0.
- SYNC: browser harness gained a consent probe group (7 checks) and a panel re-render after its state reset, so the permission probes no longer depend on when the panel was last painted.
- ADAPT: `wireEvents` now subscribes to the two Core events in addition to the host events; the subscription is still guarded so repeated `initialize()` calls cannot double-subscribe.
- ADAPT: `initialize()` renders the consent prompt at boot, which catches requests raised before the UI subscribed.
- NO-CHANGE: `Loom Host/*` — the request flow is Core+UI; the host only declares permissions.
- NO-CHANGE: the panel's permission section semantics; it still lists declared permissions and grants.
- CONFIRM: whether a denial should be remembered (session or persisted). Deliberately not implemented in this increment; see Risks.

## Architecture / API / data

- New public API: `requestPermission`, `listPermissionRequests`, `resolvePermissionRequest`; two new Core events; one new runtime-info field.
- Requests live in Core memory only. They are intentionally not persisted: a prompt that survives a reload would re-ask for something the user never saw.
- The view engine's first production consumer; no contract change was needed to support it, which was the point of building the declarative tree abstraction first.

## Compatibility / migration

Additive. Existing grants, capabilities and events are unchanged. Extensions that never call `requestPermission` behave exactly as before (they still receive `PERMISSION_DENIED`).

## Validation

- `npm test`: **pass, 99 tests** (was 84). New: request lifecycle and persistence of an approved decision; request/resolution event payloads and denial semantics; de-duplication and already-granted short-circuit; stale-id and invalid-argument handling; prompt dropped on unregister; approval after an extension disappears cannot grant; 9 consent-builder tests covering names, declaring capabilities, undeclared-permission warning, ordering, per-button request wiring, missing handlers, reasons and stable ids.
- `npm run verify:browser`: **45/45 checks pass** against SillyTavern 0.12.0, run twice back to back with identical results. New checks: the consent card appears with reason and declaring capability, approving through the prompt grants, the card clears, denying leaves the permission unheld and leaves no open request.
- The stale-toggle bug was reproduced (a run reported `before=true` when the reset had already revoked the grant), diagnosed with `LOOM_DEBUG=1`, fixed, and confirmed by two clean consecutive runs.

## Failed checks and corrections (recorded, none hidden)

1. A first Core test declared an unused `requested` array and asserted a meaningless `length === 0`; removed rather than left as fake coverage.
2. The browser run after adding the consent probe showed `loom-host` holding `host.worldinfo.write` and a toggle flipping from a stale `before=true`. Diagnosis (`LOOM_DEBUG` dump of `listPermissions()` at reset and after the toggle) proved the grant table itself was correct and the *rendered attribute* was stale — a real UI bug, fixed by reading Core at click time. The harness also now re-renders the panel after its reset.
3. An `edit` accidentally removed a bullet from `PROJECT_STATE.md` instead of adding after it; re-read and restored the bullet before continuing.

## Risks / outstanding

- A denial is not remembered, so an extension may re-request and re-prompt. There is no "don't ask again" state beyond the explicit panel toggle.
- Requests can accumulate if an extension asks repeatedly for different permissions; nothing rate-limits or expires them.
- The prompt is informational text plus two buttons; it does not yet show the capability contracts that would let a user judge the risk.
- Consent grants can still be bypassed by a script calling `grantPermission` directly — unchanged, documented boundary, not a sandbox.
- Mobile layout of the prompt is CSS-only; no browser verification at phone widths.
