# CHG-20261121-028

- Date: 2026-11-21 (Asia/Shanghai)
- Type: FEATURE, API, BUILD, TEST, DOCS
- Requirement / motivation: The P0 gap from the status review — a framework is not usable if nobody can install an extension into it. Until now an extension could only be loaded by code that already knew its URL (`importExtension`), so third-party packages had no path to a running Loom. This change adds discovery, installation, persistence and uninstallation, plus the first bundled example package.
- Stage: self-planned goal `goal-3662d29a`, P0 item 1 (extension discovery and installation).

## Changes

### Package convention (`extensions/<id>/`)

- `manifest.json`: `{ id, name, version, entry, description?, dependencies?, permissions? }`. `id` must match the directory name; `entry` must be an existing `.js` file; dependencies/permissions are validated against Core's own patterns.
- The entry module's default export is `{ activate?, deactivate? }` or a function returning it. Identity comes from the JSON manifest, hooks from code — a package needs both, and neither alone is enough.

### `npm run extensions:index` (`scripts/extensions-index.mjs`)

The browser cannot list a directory, so discovery needs an index. The script scans `extensions/`, validates each package, and writes a **deterministic** `extensions/index.json` (sorted, no timestamps, so a regenerated file only changes when a package does). Invalid packages are reported with their problems and exit the script non-zero instead of disappearing silently.

### Bundled install at boot

`Loom UI` fetches `extensions/index.json`, normalises it (`installer.js: normalizeIndex`) and imports each package through `importExtension(entry, { manifest })`. A missing index is not an error: a Loom install with no bundled extensions is valid.

### User install, persistence, uninstall

- `LoomUI.installExtension(url)` imports a module URL (relative to Loom's root, or absolute), remembers `{ id, entry }` in `loom-ui`'s persisted state, and re-imports it on the next boot.
- `LoomUI.uninstallExtension(idOrEntry)` unloads the extension and forgets the record.
- `LoomUI.getInstalledExtensions()` returns bundled + installed rows with their runtime state and error message.
- The panel gained an install section: URL input, a row per extension with its state (built-in / manual, active / failed), an error line for a failed import, and a remove button for manual installs. Bundled packages are not removable from the panel — they are files that ship with Loom (recorded as a limitation).

### Loader: package manifest + module hooks

`importExtension` used to take `options.manifest` as a **replacement** for the module's export; a `manifest.json` package would then lose its `activate` hook (or, with the old code, ignore the JSON identity). It now merges both (`mergeManifests`): the explicit manifest wins field by field, but `activate`/`deactivate` are kept from code when the JSON manifest has none. This is what makes the package convention possible without duplicating identity in code.

### Example package `extensions/hello-loom`

Registers `hello.greet` (`{ name }` → `{ message, calls }`), counts calls and persists the count through Core state. It is both the minimal reference package and the fixture for bundled-discovery verification. It declares no permissions, so loading it raises no consent prompt.

## Horizontal impact

- SYNC: `importExtension` semantics changed for callers that pass `options.manifest` **and** a module export — they now get a merge instead of replacement. Existing tests cover both old shapes (manifest-only, module-only) and stay green.
- SYNC: panel layout grows an install section; the existing registry/capability/permission sections are untouched.
- ADAPT: the browser cleanup no longer requires `extensionSettings.__loom` to be absent — bundled packages legitimately persist their own state (`hello-loom`). It now asserts no probe namespaces, no grants, no installed records.
- NO-CHANGE: capability execution, permissions, host adapter, world/chat/character writes.
- CONFIRM (open): bundled packages cannot be disabled from the panel; a user who wants to remove one deletes its directory and regenerates the index.

## Verification

- `npm test`: **222 tests pass** (216 before; +6 installer pure-function tests, +6 index-generator tests, +2 loader merge tests, adjusting counts).
- `npm run extensions:index`: indexes `hello-loom`, writes `extensions/index.json`.
- `npm run verify:browser`: **129/129 checks pass**. New checks: the bundled index is served and lists `hello-loom`; the bundled package is `active` and `hello.greet` returns `Hello, Loom!`; the panel lists it in the install section; a data-URL module installs, appears in the persisted list, is restored after a **real page reload**, and uninstalls cleanly. No leftovers: the scratch chat/card/world books are removed, no probe namespaces, no grants.

## Risks / outstanding

- `extensions/index.json` is a generated, committed file: a new package added without running the script is invisible until someone regenerates. The panel shows nothing rather than guessing — acceptable for now, but a pre-commit hook or a watcher would be better.
- User-installed modules are fetched from arbitrary URLs on every boot. That is code execution at the user's request, but it means a URL that later changes content runs new code; there is no integrity check (the identity fingerprint detects duplicate/conflict, not maliciousness).
- A failed import keeps its installed record so the error stays visible. If the module never becomes available, the row stays failed until removed — recovery is manual.
- Bundled packages have no enable/disable switch yet.
