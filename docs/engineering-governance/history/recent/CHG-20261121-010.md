# CHG-20261121-010

- Date: 2026-11-21 (Asia/Shanghai)
- Type: FEATURE, API, TEST, DOCS
- Requirement / motivation: Core requirements §2.1 lists what extensions must be able to read — 角色卡、世界书及其条目、当前聊天和聊天记录 — and §5 requires read and write capabilities to be defined separately. The adapter only exposed counts, names and a chat id, so no extension could build a world-book manager, a character inspector or any chat-aware feature without reaching into `SillyTavern` internals itself. This change closes that read gap for the three highest-value data sources.
- Stage: next stage after the permission work (CHG-20261120-008, CHG-20261121-009); this is the first increment that consumes the permission model for a read path.

## Changes

### Host (`Loom Host/index.js`, 0.9.0 → 0.10.0)

- `chat.messages` — returns the newest messages as `{ index, name, isUser, isSystem, text, truncated }`, oldest-first, with `limit` (1–100, default 20) and `offset` (counts back from the newest). Gated behind **`host.chat.read`**.
- `worlds.entries` — loads a world book through `getContext().loadWorldInfo()` and returns `[{ uid, comment, keys, secondaryKeys, content, enabled, constant, selective, order, truncated }]`, sorted by `order` then `uid`, with an optional `limit` (1–200). Ungated.
- `characters.get` — resolves a character by name or avatar filename (case-insensitive) into `{ name, avatar, description, personality, scenario, firstMessage, exampleMessages, creatorNotes, tags }`, or `null` when absent. Ungated.
- Text bounds: message and world-entry `content` are truncated at 2000 characters and flagged with `truncated`, so a single capability call cannot hand a consumer an unbounded payload.
- Host mapping stays primitive-only: `extra`, `swipes`, `swipe_id`, API keys and any other host internals are never forwarded.
- `HOST_UNSUPPORTED` is raised when a SillyTavern build does not expose `loadWorldInfo`, instead of silently returning an empty list.

### Gating decision (recorded because it is a product-visible rule)

`chat.messages` is the only gated read. Rationale: chat content is the user's private conversation and is not displayed by SillyTavern in a machine-readable list, whereas world books and character cards are library assets the host already shows in its own UI. Making every read require a grant would turn ordinary browsing into a permission ceremony and contradict "读写能力应分别定义" — the requirement asks for read/write separation, not for gating reads wholesale.

## Horizontal impact

- SYNC: host capability list assertion (8 → 11 capabilities), and the per-capability permission assertion now covers `chat.messages` / `worlds.entries` / `characters.get`.
- SYNC: version markers (Core `LOOM_VERSION`, Host `HOST_VERSION`, manifest, package).
- NO-CHANGE: `Loom UI/*` — the panel enumerates capabilities from the registry, so the new ones appear without UI edits; the permission section also picks up `host.chat.read` automatically because it derives rows from declared `permissions`.
- NO-CHANGE: `settings.*` capabilities and the permission store.
- NO-CHANGE: SillyTavern source. `loadWorldInfo` is taken from `getContext()`, which is a public context field, so the adapter does not import ST internals.

## Architecture / API / data

- Three new read capabilities; two ungated, one gated. All additive.
- New permission name: `host.chat.read`.
- New error code: `HOST_UNSUPPORTED`.
- Output shapes are flat records with primitives only, which keeps capability contracts serializable and testable.

## Compatibility / migration

Additive; existing capability ids, outputs and permissions are unchanged. Consumers that never call the new capabilities are unaffected. Existing installs gain `host.chat.read` as an optionally grantable permission, visible in the panel.

## Validation

- `npm test`: **pass, 78 tests** (was 73). New coverage: chat slicing with absolute indexes and offset, denial without `host.chat.read`, default limit on `null` input, truncation at 2000 chars, world entry mapping and ordering (including `enabled` inversion from `disable`), empty book and missing book returning `[]`, `HOST_UNSUPPORTED`, and character lookup by name, by avatar and not-found → `null`.
- `node --check` on `Loom Host/index.js`: pass (re-run after the version bump).
- Not run: browser verification against a live SillyTavern 0.10.0 (stubbed contexts only), and no real world-book file was loaded through `loadWorldInfo` in a browser. Outstanding.

## Failed checks and corrections (recorded, none hidden)

1. The capability-list assertion failed after adding the three capabilities — expected, and updated to the new contract rather than loosened.
2. First draft of `chat.messages` used `input.limit` directly, which throws on `null` input. Fixed by accepting `['object', 'null']` and normalising `input ?? {}` through the capability schema.
3. Considered gating world books and character cards as well. Rejected: it would make every browsing flow require a grant; the requirement asks for read/write separation, not blanket read gating. The rationale is recorded above so a later instance does not flip it silently.

## Risks / outstanding

- Chat messages are windowed, not streamed: a long chat needs several calls, and there is no cursor/pagination token yet.
- `worlds.entries` depends on `getContext().loadWorldInfo`, which ST caches per name; a stale cache returns stale entries until the host reloads it. There is no cache-invalidation capability.
- World entry `content` truncation at 2000 chars can cut a long entry; a consumer that needs full text must be given a follow-up capability rather than a larger cap here.
- Writing back (world book save, chat injection, character edit) is still not implemented — deliberately: `saveWorldInfo` needs merge semantics and an explicit write contract before it is safe to expose.
- Browser verification of 0.10.0 is outstanding.
