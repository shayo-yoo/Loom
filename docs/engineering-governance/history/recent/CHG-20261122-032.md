# CHG-20261122-032

- Date: 2026-11-22 (Asia/Shanghai)
- Type: FEATURE, API, TEST, DOCS
- Requirement / motivation: P1 item 1 from the stage goal. `worlds.rename` refused any book bound to a character card because the adapter could not write cards (CHG-20261121-024). CHG-20261121-025 added `characters.update`, so the blocker is gone — but silently rewriting user cards during a rename would also be a blast-radius problem, so the migration had to be explicit and separately authorised.
- Stage: self-planned P1 goal `goal-c4b5aa5a`, item 1.

## Design

Three decisions define the behaviour:

1. **Opt-in, not automatic.** `migrateCards` defaults to absent/false, so the pre-existing refusal remains the default; a caller must ask for link rewriting. `details.hint: 'migrateCards'` tells a refused caller what to do.
2. **A separate grant.** Rewriting cards is a card write even though the rename itself is a world-book operation. With `migrateCards: true` and at least one bound card, the adapter requires `host.characters.write` and returns `PERMISSION_DENIED` (`details.missing`) without touching anything otherwise. This uses the handler's `contextInfo.hasPermission` (Core already passes it), so no new Core concept was needed.
3. **Links vs copies.** `extensions.world` is a link and can be rewritten; a card's embedded `character_book.name` is a copy of a book inside the card and cannot be renamed by renaming the world book. Embedded copies therefore keep blocking (`WORLD_IN_USE`, `details.embeddedBooks`) even with migration enabled — the previous code conflated the two.

## Ordering and failure

The write order is now: copy the book → verify it is registered → migrate the chat binding → migrate the persona binding → rewrite card links → delete the old book → verify it is gone.

Card links are intentionally moved **before** deletion, so a failure leaves the old book in place and every reference still resolves. A partial failure returns `CARD_LINK_MIGRATION_FAILED` with the failing avatars; the successful rewrites are already applied and the new copy exists (reported by presence), which the record and the API index state explicitly. A caller can retry: already-migrated cards are rewritten to the same target, which is idempotent.

## Changes

- `characterReferences` now returns `{ bound, embedded }` instead of one merged name list; both call sites (rename refusal and migration) use the split.
- `worlds.rename` input adds `migrateCards?: boolean`; the capability description and the API table say when it is needed.
- `execute` takes the Core-supplied `contextInfo` and checks `hasPermission('host.characters.write')` only when a migration is actually required.
- Card rewrites go through `/api/characters/merge-attributes` (`{ avatar, data: { extensions: { world: to } } }`) and refresh the in-memory copy with `getOneCharacter`, mirroring `characters.update`.
- Failure details name the cards that failed and the migrations already applied.

## Horizontal impact

- SYNC: the existing refusal test still passes — default behaviour is unchanged except for the added `hint` in `details`.
- SYNC: the rename ordering changed (deletion moved after migrations); the plain rename test's assertions on `migrated` and book state are unchanged.
- ADAPT: the browser harness gained a real link-migration probe (create book + card, link them through the host endpoint, rename with `migrateCards`, read the card back).
- NO-CHANGE: `characters.update`/`create`/`remove`, chat and persona binding migration, copy-then-delete ordering for the book itself.

## Verification

- `npm test`: **240 tests pass** (237 before; +3: migration with both grants, permission/embedded refusal, failed migration keeps the old book).
- `npm run verify:browser`: **151/151 checks pass**. New: a bound card blocks the rename by default; `migrateCards: true` rewrites the card's `extensions.world`, renames the book, and leaves the old name gone; the harness cleans up the scratch card and both book names.

## Risks / outstanding

- A rename with `migrateCards` can rewrite several cards; a partial failure leaves a mixed state (some cards on the new name) with the old book still present. The error lists what failed, but there is no automatic rollback of the rewrites.
- Cards are rewritten one request at a time; a large library makes the rename slower (no batching yet).
- The globally activated book still refuses regardless of `migrateCards` — the host rebuilds that dropdown (recorded in CHG-20261121-024).
- Character-card links are not versioned: a concurrent card edit during the migration could be overwritten for the `extensions` block only (merge-attributes merges that block).
