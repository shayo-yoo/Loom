# CHG-20261121-029

- Date: 2026-11-21 (Asia/Shanghai)
- Type: FEATURE, API, TEST, DOCS
- Requirement / motivation: P0 items 2 and 3 from the status review — Loom had an install path (CHG-20261121-028) but no developer-facing guide and nothing a normal user could actually do with it. A framework whose value can only be inferred from governance documents is not deliverable.
- Stage: self-planned goal `goal-3662d29a`, P0 items 2 (guide + example) and 3 (user-visible product).

## Changes

### Developer guide and README

`docs/guides/writing-an-extension.md` walks from an empty package to a working extension: package layout, manifest field table, hook contract, capability registration with the supported schema subset, the two permission declaration points (manifest vs capability), consent, state and events, the view API (`createView`, node shape, `setProps`/`setChildren` paths, event payload shape, controlled `tabs`/`modal`), install steps, and a failure table. `README.md` gives the one-screen summary and points at the guide.

The guide is written against the code, and writing it exposed three real API facts that are now documented there: `button` uses `label` (not `text`), event handlers receive `{ event, payload, path, viewId, extensionId }`, and `worlds.entry.update` takes a **string** uid.

### UI components gained what real editing needs

- `textarea` (17th built-in): multiline editor, `change` on blur, `rows` clamped to 1..40, and an update that never clobbers what the user is typing.
- `select` options now accept `{ value, label }` as well as plain strings, so a caller can show "12 · 备注" while keeping `"12"` as the value. The string form is unchanged.

### `extensions/world-book-manager` — a user-visible product

A floating launcher opens a panel that lists world books, lists an entry's uid/comment, and edits **comment, enabled and content**, saving through `worlds.entry.update` and reporting the real outcome ("条目 0 已保存。", or the host's error text). It declares `host.worldinfo.write`, so activation raises the consent prompt — the manager demonstrates the permission path rather than assuming it.

Two correctness decisions inside it:

- **It reads through `worlds.export`, not `worlds.entries`.** The latter truncates content at 2000 characters for display; editing truncated text and saving would destroy the entry.
- **`uid` is sent as a string**, matching the capability contract (a numeric uid is rejected with `INVALID_INPUT` — found by the browser probe, not by reading the code).

The panel is rebuilt on each `change` (the alternative, partial `setChildren`, would need stable node paths for a tree that changes shape). Rebuilding on blur only means the textarea is never re-created mid-typing.

## Horizontal impact

- SYNC: `select` option normalisation is shared by `createSelect`/`updateSelect`, so both mount and update paths accept the new form; existing string-option callers are unaffected and covered by a test.
- SYNC: `textarea` is a new component id; the panel's component count and the guide's list were updated together.
- ADAPT: the consent probe had to become request-scoped. The manager's declared permission adds a standing pending request, and clicking "the first 允许 button" then approved the wrong extension. The probe now finds the block for its own extension name; the "no open request" assertion was likewise scoped to the probe.
- ADAPT: the world-book-manager probe re-registers `verify-probe` because the install probe reloads the page, which drops dynamically registered extensions.
- NO-CHANGE: capability contracts, host adapter, installer logic.

## Verification

- `npm test`: **230 tests pass** (222 before; +2 textarea, +1 select option form, plus the existing suite).
- `npm run verify:browser`: **136/136 checks pass**. New: the manager activates as a bundled package; launcher and hidden panel are mounted; opening it lists a scratch book (81 options in the harness session); selecting the book and entry, editing the textarea and clicking 保存 produces "已保存" in the panel **and** the new content in the world book; the panel closes from the launcher. The scratch book is removed in cleanup.
- The consent probe still passes with multiple pending requests.

## Risks / outstanding

- The manager edits one entry at a time; no create/delete, no key editing, no multi-select, no search. It proves the path, not a full editor.
- The panel is fixed-position DOM owned by the extension (inline styles), not a Loom-hosted panel slot; a second extension wanting the same corner would collide. A shared panel container is a future UI-system item.
- The manager rebuilds the whole view on every change: acceptable for a few dozen books, not for a large library (no virtualisation yet).
- `textarea` emits `change` on blur only; a caller wanting live updates would need an `input` event, which the component does not emit.
