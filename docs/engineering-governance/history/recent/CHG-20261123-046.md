I had said the block *renderer* could live in an extension; the user pointed out that Loom UI exists precisely to own interaction and rendering, so **the capability to render interactive content belongs in Loom UI**, and only the *authoring* side (a visual creator) and concrete widget sets are optional extensions. "不能把提供交互能力的基础独立出去".
- Stage: branch `feature/block-rendering`.

## Decision (supersedes my earlier statement)

| Concern | Where it belongs | Why |
|---|---|---|
| Block parsing / prompt stripping | Core (`markers.js`) + Host (prompt filter) | Already landed in CHG-045; the grammar and the "not in context" guarantee are framework-level |
| **Rendering a block into interactive Loom UI** | **Loom UI** (`blocks.js`) | UI owns interaction and rendering; putting it behind an extension would make the foundation optional |
| Which widgets exist (inventory, level, character panel) | extensions | business content |
| Visual creator / builder | an extension | explicitly optional |

This is recorded because it reverses what CHG-045's summary implied, and the architecture doc must not keep the wrong boundary.

## Changes

### `Loom UI/blocks.js` (new)

- `registerBlock(extensionId, { id, name?, build(context) })` — one widget kind per id, owned by an extension; `build` returns a normal view node. Registered through the same cleanup mechanism as everything else, so unregistering the owner removes both the kinds and the live mounts.
- `renderBlocksIn(body, { messageId, message })` — replaces each block in one rendered message body with a `.loom-block` container and mounts a view inside it. It touches **text nodes only**, so SillyTavern's own markup (avatars, swipe buttons, timestamps) is never rebuilt, and no message content is parsed as HTML.
- `refreshBlocks(root?)` — walks `.mes[mesid]` under a root (default `#chat`); messages without a block are skipped entirely, so cost is proportional to widgets, not chat length. A message that lost its block has its stale mounts dropped.
- `disposeMessageBlocks`, `listBlockMounts`, `listBlocks`, `unregisterBlocks`, `resetBlockMounts` complete the lifecycle.
- **Degradation:** an unknown kind becomes a hidden placeholder (the marker is never left visible), and a `build` that throws becomes a hidden placeholder carrying `data-loom-error` — a broken widget cannot take the message with it.
- **Re-render safety:** every render disposes the message's previous mounts first, so SillyTavern rebuilding a body produces one widget, not two.

### Wiring

- `LoomUI.registerBlock` / `listBlocks` / `refreshBlocks` / `disposeMessageBlocks` on the facade.
- `wireEvents` re-renders blocks on `host:message:received` and `host:chat:changed` (deferred with `setTimeout(…, 0)` so the host finishes its own DOM work first) and logs rather than throwing if a refresh fails.
- `.loom-block` styles: block flow, `min-width: 0`, and `pointer-events: auto` on children so a widget inside a message stays clickable without a click falling through to the message editor.

## Direct scope

`Loom UI/blocks.js` (new), `Loom UI/blocks.test.js` (new), `Loom UI/index.js`, `Loom UI/style.css`, `tests/browser/verify.mjs`, API index, architecture, project state, version markers.

## Horizontal impact

- SYNC: capability-free (no new host capability); the facade gained four members, which the guide will document.
- SYNC: the browser probe renders into a **detached fixture element**, never into the user's chat, because the renderer accepts any root. This keeps the harness inside the "only touch data you created" rule.
- ADAPT: `refreshBlocks` defaults to `#chat`, but accepts a root so tests and probes never need to mock the chat container.
- NO-CHANGE: the block grammar, the prompt filter, and the existing view engine — widgets are ordinary views.

## Verification

- `npm test`: **289 tests pass** (+10 block tests: in-place rendering, unknown kind hidden, throwing builder contained, re-render replaces instead of duplicating, multiple blocks across text nodes, refresh skipping plain messages, stale mounts dropped, unregister cleanup, registration validation, idempotent dispose).
- `npm run verify:browser`: **204/204 checks pass** (three consecutive runs). New: a registered kind renders `HUD hp=7` inside a synthetic message with the marker gone and a plain message untouched; a rebuilt body keeps exactly one widget; an unknown kind is hidden; unregistering the owner removes its widgets and kinds.

## Risks / outstanding

- Blocks are rendered for messages present in the DOM. A very long chat with many widgets re-renders them all on refresh; the cost is bounded by the number of blocks, not messages, but there is no viewport-based lazy mounting yet.
- Interaction inside a message still competes with SillyTavern's own message click handlers; the CSS only guarantees the widget receives the event first. Per-widget `stopPropagation` is the extension's job.
- No authoring tool, no widget set, and no persistence of widget state beyond what an extension stores in its own state — those remain out of scope by design.
- A message edited inside SillyTavern keeps its block in the stored text (correct: the block is the UI's anchor), so exports contain the marker; stripping on export is still a future item.
