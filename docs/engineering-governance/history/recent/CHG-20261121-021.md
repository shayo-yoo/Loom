# CHG-20261121-021

- Date: 2026-11-21 (Asia/Shanghai)
- Type: FEATURE, API, DATA, TEST, DOCS
- Requirement / motivation: Core requirements §6 asks for state read/update interfaces and §8 for runtime state management; PROJECT_STATE has carried "state and events are page-scoped and lost on reload" since the first increment, which makes any extension with durable user progress impossible without bypassing Loom and calling the host directly. Grants were already persisted (CHG-20261121-009); state was the remaining half.
- Stage: self-planned goal `goal-dbba54ec`, increment 1 (persistence before write-back, because a write path without durable state cannot remember what it did).

## Design decisions

1. **Purpose-specific store, not a generic storage port.** `setStateStore` mirrors `setPermissionStore`: Core owns namespace isolation, the store only reads and writes one extension's snapshot. A general `storage.get/set` port was rejected again — two consumers with different snapshot shapes do not justify an abstraction that would leak keys to every caller.
2. **Snapshot per extension namespace.** `load(extensionId) → object|null`, `save(extensionId, snapshot)`, `remove(extensionId)`. A snapshot is a plain object of the extension's own keys; `null` means "nothing to persist", which removes the namespace rather than storing an empty object.
3. **Only cloneable values are persisted.** `structuredClone` is the gate: functions, DOM nodes and other live objects stay usable in memory but are skipped from the snapshot with one warning that counts them. Persisting them would either throw or silently substitute something on the next load; skipping is the honest option and the live value is unaffected.
4. **A live value is never clobbered by a snapshot.** When the store attaches after an extension already wrote state, restore only fills missing keys. Otherwise attaching a stale store could overwrite in-memory truth.
5. **Store failures are reported, never fatal.** `load`/`save`/`remove` run inside guards; a broken store leaves the in-memory namespace intact and logs a warning.

## Changes

### Core (`Loom Core/index.js`, runtime 0.18.0 → 0.19.0)

- Added `setStateStore(store | null)`. Attaching restores state for every registered extension; registering an extension afterwards loads its own snapshot, so boot order does not matter.
- `setState`/`deleteState` persist the namespace after each change; deleting the last key removes the stored namespace.
- `unregisterExtension` removes the persisted namespace.
- `getRuntimeInfo()` gained `stateStoreAttached`.

### Host (`Loom Host/index.js`, 0.18.0 → 0.19.0)

- Installs a state store under `extensionSettings.__loom.state[extensionId]`, sharing the reserved root with the grant table so one SillyTavern settings save covers both. `saveSettingsDebounced` flushes after every write/remove.
- The reserved root is created lazily; a missing host means `load` returns `null` and `save`/`remove` are no-ops (state still works in memory).

## Direct scope

`Loom Core/index.js`, `Loom Core/index.test.js`, `Loom Host/index.js`, `Loom Host/index.test.js`, `tests/browser/verify.mjs`, version markers, docs.

## Horizontal impact

- SYNC: `Loom Core/index.js` exports/API gained `setStateStore`; `getRuntimeInfo()` grew a field.
- SYNC: the host now attaches two stores; both share `__loom`, so the doc's storage description covers grants **and** state.
- NO-CHANGE: `settings.*` capabilities remain the caller-scoped, user-facing channel; state is a different concept (runtime bookkeeping, no schema, no permission). The distinction is documented rather than merged.
- NO-CHANGE: permission store semantics; the shared `loomSettingsRoot` helper is a refactor with identical behaviour, covered by the existing grant tests.
- CONFIRM: whether state should also be readable/writable through a capability. Not added: exposing state to other extensions would need ownership rules that `settings.*` already models better.

## Validation

- `npm test`: **180 tests pass** (172 before; +8: five Core cases for restore/persist/skip/failure/detach, two Host cases for the reserved root and the host-unavailable path, plus the import wiring).
- `npm run verify:browser`: **87/87 checks pass**. New browser checks: state lands in `extensionSettings.__loom.state`, a non-cloneable value stays in memory without being persisted, deleting the last key drops the namespace, and **state survives a real page reload** and is restored when the extension registers again.
- The reload assertion is a genuine `Page.navigate`, not a stub.

## Failed checks and corrections (recorded, none hidden)

1. `setStateStore` was not imported in `Loom Core/index.test.js`, so five new tests failed with `ReferenceError`. Added to the import list; the implementation was fine.
2. A first draft kept a `pendingState` map for snapshots loaded before registration, then the registration-time `load` made it dead code. Removed rather than left as unused machinery.
3. The host had duplicated settings-root logic; it was factored into `loomSettingsRoot`, and the existing grant tests were re-run to confirm identical behaviour.

## Risks / outstanding

- Snapshot writes are whole-namespace: every `setState` rewrites that extension's snapshot and triggers a debounced SillyTavern save. Fine for small state, wasteful for large.
- State is restored only at registration; a store attached mid-session loads registered extensions once and does not watch for external edits.
- `structuredClone` is the only serialization gate, so values that clone but are not meaningful across reloads (class instances become plain objects) lose their prototype silently. Extensions should persist plain data.
- Events remain page-scoped by design; only state is persisted.
- The host keeps state and grants in one settings object; a corrupted `__loom` node disables both (each store guards its own reads, so it degrades rather than crashes).
