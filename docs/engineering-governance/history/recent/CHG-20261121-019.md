(a) CHG-20261121-018 left the consent prompt showing only "which capability needs this permission", so the requirements' informed-consent intent (shared interface agreement §4 "interfaces must describe inputs, outputs and errors"; §7 "understandable feedback") was not met — a user could not judge what a grant allows. ## Consent prompt shows contracts

- `Loom UI/consent.js` gained `describeContract(schema)`: a compact one-line summary of a capability schema — `无` for null, `数组<T>` for arrays, `{ a, b, c, d, +N }` for object schemas (required fields, truncated at four), `<type> 枚举`, and `string|null` for type unions.
- `summarizeRequests` now returns `contracts` next to `declaredBy`, so the prompt can render `输入 … → 输出 …` for the capability that requires the permission.
- The prompt keeps the existing "所需能力：" line and adds the contract line; a permission with no declaring capability still shows the warning text.

## Manifest discovery and boot sequence

`Loom Core/loader.js` gained two functions:

- `startExtensions()` — activate every loaded extension in dependency order. Order is computed (Kahn), not declarative, so an extension loaded before its dependency still starts after it. Independent extensions keep load order. Returns `{ activated, failed }`; failures never throw, and a dependency cycle leaves its members `failed` with `DEPENDENCY_MISSING` rather than hanging or throwing.
- `importExtension(specifier, { activate?, manifest? })` — dynamic `import()` of a module whose manifest is a default-export object, a default-export factory function, a `manifest` named export, or supplied via options. Import errors, factory throws, missing manifests and invalid manifests all come back as structured failures (`IMPORT_FAILED`, `MANIFEST_FAILED`, `MANIFEST_MISSING`, `MANIFEST_INVALID`) with `state: 'failed'`; the caller gets a report, not an exception. `activate: false` stops at `loaded`.

Both are exposed on `globalThis.Loom` and as named exports.

## Failed checks and corrections (recorded, none hidden)

1. A first assertion expected an independent extension to start in an alphabetical position; the implementation uses load order among unconstrained nodes. The test was wrong, not the code — it now asserts the dependency constraint plus full membership, and the ordering rule is documented.
2. The consent summary test initially expected a contract where the fixture declared none; the fixture was right and the expectation was corrected (`无`).
3. The first browser probe produced `SyntaxError` because the module source string spanned a newline inside a double-quoted literal. Collapsed to one line; the probe now runs.

## Risks / outstanding

- `describeContract` summarizes, it does not validate; a caller reading the prompt still cannot see enum values or nested shapes.
- Contracts render only for the first declaring capability of a permission; a permission declared by several capabilities shows one representative contract.
- `startExtensions` has no timeout and no partial-restart: activation is synchronous by contract, so an extension that leaves work pending is responsible for it.
- `importExtension` trusts the module's own `id`; two packages claiming the same id will conflict at load (`already loaded` / `already registered`), reported as `MANIFEST_INVALID`.
- Dynamically imported modules cannot be unloaded from the browser's module registry; `unloadExtension` removes the Loom registration and runs cleanups, but the module code stays loaded. Recorded because it affects "reinstall" flows.
- No discovery of manifests on disk or from the host; a host that knows its extension URLs must call `importExtension` per package.
