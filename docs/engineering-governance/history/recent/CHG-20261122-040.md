# CHG-20261122-040

- Date: 2026-11-22 (Asia/Shanghai)
- Type: FEATURE, API, TEST, DOCS
- Requirement / motivation: the interface contract lists "复合组件" (composite components) among resources that should carry a stable identity, and the requirements say extensions should be able to create and reuse custom UI components. Until now only atomic components existed; nesting was possible only by hand-writing trees inside each view, with no name, props or reuse unit.
- Stage: branch `feature/identity-and-contract-gaps`, second batch.

## Design

A composite is a **named view tree** registered as a normal component:

```js
LoomUI.registerCompositeComponent('my-ext', {
    id: 'greeting',
    name: 'Greeting',
    props: { name: { type: 'string', default: 'world' } },
    build: props => ({ component: 'text', props: { text: `Hello ${props.name}` } }),
});
```

- It goes through `registerComponent`, so it gets the same identity, prop validation, events, serialization and cleanup as atomic components — no second component system.
- `build(props, context)` returns a view node; the composite mounts it as a **nested view** inside its own element (`.loom-composite`).
- `update` destroys the previous nested view and renders a new one; `unmount` destroys it too, so a composite cannot leak a view when the parent tree changes or the extension unloads.
- Because the id lives in the global component registry, another extension can use a composite by id, and the owning extension's unregister removes it.

## Direct scope

`Loom UI/composite.js` (new), `Loom UI/composite.test.js` (new), `Loom UI/index.js` (facade), `Loom UI/style.css`, docs, version markers.

## Horizontal impact

- SYNC: the facade gains `registerCompositeComponent(extensionIdOrDefinition, maybeDefinition)`, matching the existing `registerComponent` overload pattern.
- SYNC: tests register built-in components in the fixture, because a composite's tree is validated against the component registry just like any view.
- NO-CHANGE: atomic components, the view engine, serialization. A composite serializes as its own component id plus props; its internal tree is part of its definition, not the serialized view (recorded as a deliberate boundary).

## Verification

- `npm test`: **253 tests pass** (composite suite: render + identity, update without leaking the nested view, nesting/other-extension reuse, validation and duplicate-id refusal).
- `npm run verify:browser`: **185/185 checks pass** (composites are covered by the unit suite; the browser run confirms no regression).

## Risks / outstanding

- `update` re-creates the nested view instead of reconciling it: cheap for small trees, but a large composite loses focus/scroll inside itself on every prop change.
- Composite definitions are not serializable (only their usage is), so a future visual editor would need a rule for editing a composite's internal tree.
- Props are validated by the component registry but the nested tree's props are the builder's responsibility; a bad `build` fails at mount, not at registration.
