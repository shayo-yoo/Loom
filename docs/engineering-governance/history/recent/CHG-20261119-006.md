# CHG-20261119-006

- Date: 2026-11-19 (Asia/Shanghai)
- Type: FEATURE, API, TEST, DOCS
- Requirement / motivation: Implement the total requirements' extension identity and duplicate-resource detection: the same identity with the same content should be recognized as a duplicate install, and the same identity with different content should be reported as a content conflict or version copy, without building author authentication, signatures, or an online trust system.
- Changes:
  - Core: `registerExtension` now accepts `author`, `declaredId`, `content`, and `contentHash`. Declared identity is `author + declaredId` (both optional; `declaredId` defaults to the runtime `id`), yielding `identityKey` such as `loom:ui`.
  - Core: added `computeContentHash(content)`, a deterministic FNV-1a 64-bit fingerprint over a string or stably serialized JSON value. This is duplicate-detection metadata, not a signature.
  - Core: added `checkInstall(candidate)`, which reports `new`, `duplicate`, or `conflict` plus `idTaken` and matching members without registering anything. Same identity + matching hashes = duplicate; same identity + different or missing hashes = conflict with a reason.
  - Core: added `listIdentityGroups()` and `listIdentityConflicts()` to group registered installs by declared identity and surface duplicate/conflict groups.
  - `Loom Host` registers identity `loom:host` with a version/feature content fingerprint; `Loom UI` registers `loom:ui` the same way.
  - Loom panel now shows an "身份冲突" row and a warning list with identity key, runtime id, version and hash for each conflicting member.
  - Bumped Core/manifest/package version to 0.6.0.
- Direct scope: `Loom Core/index.js`, `Loom Core/index.test.js`, `Loom Host/index.js`, `Loom UI/index.js`, `Loom UI/style.css`, `manifest.json`, `package.json`, governance docs.
- Horizontal impact:
  - SYNC: `listExtensions()` records now include `author`, `declaredId`, `identityKey`, `contentHash`; tests and consumers relying on the old exact shape were updated.
  - ADAPT: Host and UI registrations supply identity/content; future installers should call `checkInstall` before registering a discovered copy.
  - NO-CHANGE: SillyTavern loader/source; the ST discovery layer still installs extensions as-is. Loom can only detect copies after it loads them, because ST performs discovery first.
  - CONFIRM: No ST install-time gate exists yet; conflict warnings are runtime-only and disappear on reload if the conflicting copy is removed.
- Architecture/API/data: Identity and fingerprints are in-memory and page-scoped. `identityKey` separates author namespaces and allows different runtime ids to represent the same declared extension. Content conflicts are reported, not blocked, so user-modified content remains usable.
- Compatibility/migration: Extensions without author/declaredId keep working; their identity is `anonymous:<id>`. No existing API removed. The record shape gained fields, documented in the API index.
- Validation:
  - `npm test`: pass, 35 tests, including hash stability across key order, declared identity registration, new/duplicate/conflict install checks, unverifiable-content conflicts, identity grouping and unregister cleanup.
  - `node --check` for Core, Host, and UI: pass.
  - ST page loaded runtime 0.6.0; `loom-host` and `loom-ui` reported `loom:host` / `loom:ui` with `fnv1a64` hashes.
  - Browser: `checkInstall` reported `duplicate` for an identical copy of `loom-ui` and `conflict` (`same-identity-different-content`) for an altered copy; panel showed 1 identity conflict with `loom:ui`; after unregister and refresh it returned to 0; no Loom console errors.
- Failed checks and corrections:
  - A test-edit replacement accidentally removed the declaration line of the existing "unregistering an extension removes its capabilities" test, leaving an orphaned body. It was restored and the suite re-run.
  - Existing exact-record assertions needed the new identity fields; updated rather than loosened.
- Risks / outstanding: FNV-1a 64 is not collision-proof and is not a security mechanism; callers may supply their own `contentHash`, and content itself is registrant-supplied, so this detects accidental duplicates/divergence, not malicious forgery. No persistence, install-time integration with ST discovery, or user-facing install prompt outside the Loom panel yet.
