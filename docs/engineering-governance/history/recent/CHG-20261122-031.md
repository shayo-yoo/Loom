# CHG-20261122-031

- Date: 2026-11-22 (Asia/Shanghai)
- Type: FEATURE, API, TEST, DOCS
- Requirement / motivation: P1 write-capability gap from the status review — Loom could edit a character card's fields but not create or delete one, so the write path was half closed and the world-book manager had no way to work with characters at all. Total requirements §7 (host interaction) wants the full lifecycle behind declared capabilities.
- Stage: self-planned P1 block, first increment (write-path completion).

## Changes

### `characters.create` (write, `host.characters.manage`)

`{ name, fields? }` → `{ avatar, name, created }`.

- A **separate permission** from `host.characters.write`: editing fields and creating a card are different blast radii, matching the world-book split (`write` vs `manage`).
- Name validation happens before any request: non-empty, ≤ 80 chars, and no path/filename characters (`\ / : * ? " < > |` and NUL) — the name becomes a filename on the host side, so a separators must fail with `INVALID_INPUT` rather than relying on server sanitising.
- A case-insensitive name collision fails with `CHARACTER_EXISTS` and reports the existing avatar; create can never overwrite.
- Initial fields reuse the `characters.update` whitelist (`description`, `personality`, `scenario`, `firstMessage`, `exampleMessages`, `creatorNotes`, `systemPrompt`, `postHistoryInstructions`, `tags`). The adapter maps them to host card keys; `tags` is written as an array.
- The endpoint is SillyTavern's own `/api/characters/create` (no `getContext()` equivalent), returning the avatar filename. The adapter refreshes `getCharacters()` and requires the new card to appear (`CHARACTER_CREATE_FAILED` otherwise) — a write that the host does not register is reported, not assumed.

### `characters.remove` (write, `host.characters.manage`)

`{ avatar, confirm }` → `{ avatar, removed }`.

- `confirm` must repeat the avatar filename **or** the character name exactly (`CONFIRMATION_REQUIRED`, with both in `details`); a stale variable cannot delete an unrelated card.
- **Refuses the currently open character** (`CHARACTER_IN_USE`): deleting it makes SillyTavern reload the chat area mid-call. The user switches away and retries.
- Deletion passes `delete_chats: false`: the card is removed, the conversation directory stays. Loom does not take user data along with a card.
- After deletion the adapter refreshes and verifies the card is gone (`CHARACTER_REMOVE_FAILED`). Unlike world books there is no cache-eviction problem here because the refresh goes through the host's own character list.

## Direct scope

## Horizontal impact

- SYNC: capability list 23 → 25; the permission table gains a `host.characters.manage` row; `API_INDEX` gains both capabilities and a lifecycle section.
- ADAPT: card creation reuses `CHARACTER_PATCH_FIELDS` and `characterPatchProperties` from `characters.update`; the mapping table stays the single source for field names.
- ADAPT: the browser probe creates a scratch card, asserts the PNG exists on disk, deletes it through the capability and asserts the file is gone — the same discipline as the world-book and chat probes.
- NO-CHANGE: `characters.update` semantics (merge-attributes, V2 `data` block), `characters.list`/`get` (ungated), world-book lifecycle.

## Verification

- `npm run verify:browser`: **145/145 checks pass**. New checks: `characters.create` writes a real PNG and lists it; a duplicate name is refused; deletion without the echo is refused; `characters.remove` deletes it and the PNG is gone from disk. The harness cleans up any leftover scratch card.

## Risks / outstanding

- Creation is single-card: no avatar upload, no duplicate/import, no batch operations.
- Deletion keeps the chat directory by design; there is no way for a caller to request chat deletion (a destructive option would need its own permission and confirmation).
- The open-character refusal means a caller must switch characters first; no "delete and switch" convenience.
- Fields are validated by the host's TavernCard V2 validation on write (the same endpoint the editor uses), so an invalid card is rejected by the host rather than by Loom.
