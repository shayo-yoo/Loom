# CHG-20261121-014

- Date: 2026-11-21 (Asia/Shanghai)
- Type: FEATURE, API, TEST, DOCS
- Requirement / motivation: CHG-20261121-011 shipped `worlds.entry.update` and recorded that create/delete were deferred because each needs its own contract (uid allocation, cascade rules). Core requirements §5 require write capabilities to be declared and bounded, and the total requirements §7 name the world-book flow as the canonical host interaction. A world-book manager cannot exist with update alone: adding a lore entry is the primary action.
- Stage: write-back completion, second increment (after CHG-20261121-011).

## New capabilities

- `worlds.entry.create` — `{ name, entry? }` → `{ name, uid, created }`, gated by `host.worldinfo.write`.
- `worlds.entry.remove` — `{ name, uid }` → `{ name, uid, removed }`, gated by `host.worldinfo.write`.

Both re-read the book, mutate it and save with `immediately = true`, so a resolved success means the host accepted the write.

## Contracts worth recording

### uid allocation mirrors the host, not "max + 1"

SillyTavern's own new-entry button allocates the **first free integer uid from 0** (`getFreeWorldEntryUid`), so deleting uid 3 and adding an entry reuses 3. Allocating `max + 1` would diverge from the host editor and leave gaps that ST later fills differently. The adapter mirrors the host rule, and treats both the object key and the entry's `uid` field as reserved because imported books can disagree between them.

### "Book exists but is empty" vs "typo in the name"

`loadWorldInfo` answers an unknown name with no entries, so emptiness alone cannot distinguish a missing book from an empty one. `worlds.entry.update`/`remove` therefore report `WORLD_NOT_FOUND` for an empty book (recorded in CHG-20261121-012). For `create` that would be wrong — an empty book is a legitimate target — but saving into a mistyped name would silently create a new book file on disk. Resolution: `create` requires the name to be present in the host's world list (`getWorldInfoNames()`). A typo fails with `WORLD_NOT_FOUND`; an existing empty book succeeds with `uid: 0`.

### Entry defaults are copied, deliberately, and will drift

New entries start from a default field set mirroring SillyTavern 1.19.0's `newWorldInfoEntryTemplate` (`WORLD_ENTRY_DEFAULTS` in `Loom Host/index.js`). Copying is a conscious trade-off: importing host internals would couple the adapter to ST's file layout, which the architecture forbids. The cost is that a host upgrade changing the entry model must update this table — recorded in `PROJECT_STATE.md` as a known maintenance point rather than left implicit.

## Validation

- `npm test`: **pass, 105 tests** (was 99). New: create with first-free-uid allocation and host defaults; create without options; uid reuse after a freed slot; uid reserved when an entry's key and `uid` field disagree; denial for create and remove leaving the book untouched; remove plus missing entry/book; create refusing an unknown book while accepting an empty one; `HOST_UNSUPPORTED`.
- `npm run verify:browser`: **54/54 checks pass** against SillyTavern 0.13.0, including a real write round-trip. The harness creates a throw-away book `__loom_verify_scratch__` through `/api/worldinfo/edit`, refreshes the host list, then runs create → read back the entry through `worlds.entries` → update (asserting the `enabled` → `disable` mapping survives a host round-trip) → remove → verify the entry is gone, and finally deletes the scratch book and asserts it is absent. Cleanup also deletes the scratch book if a probe failed midway.
- Verified on disk: no `*loom*` file remains under `data/default-user/worlds`.
- Not run: world-entry create/remove through the ST editor UI, and no verification of how a created entry renders in SillyTavern's own world-info panel. The harness proves the data, not the host's rendering.

## Failed checks and corrections (recorded, none hidden)

1. A test asserted an empty book should return `WORLD_NOT_FOUND` while its stub lacked `saveWorldInfo`; the actual code correctly returned `HOST_UNSUPPORTED`. The test setup was wrong, but reviewing it exposed the real design question above, which changed the implementation to use host membership.
2. The first write-probe draft embedded `${JSON.stringify(uid)}` inside plain JavaScript (not a page-evaluated template), which broke parsing. The three occurrences were corrected to compare against the local `uid` variable.
3. `stubWorldBook` originally stubbed no world names, so every create failed with `WORLD_NOT_FOUND`; the helper now provides `getWorldInfoNames` and supports a `hidden` option for the missing-book case.

## Risks / outstanding

- Last-write-wins remains: no revision token, so a concurrent editor can still overwrite an unpatched field.
- `create` cannot create a book, and `remove` cannot delete one; the whole-book lifecycle is intentionally unimplemented because deletion needs a confirmation surface.
- The entry default table drifts with host upgrades (recorded above).
- Creating an entry does not validate that `keys` are non-empty; a keyless non-constant entry is inert in ST. Validation is left to the extension so Loom does not encode business rules about what a useful entry is.
- Browser verification of the ST editor rendering of a created entry is missing.
