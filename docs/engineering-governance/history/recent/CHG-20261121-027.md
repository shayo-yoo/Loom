# CHG-20261121-027

- Date: 2026-11-21 (Asia/Shanghai)
- Type: FIX, TEST, DOCS
- Requirement / motivation: `chat.append` (CHG-20261121-022) shipped `type` defaulting to `narrator`, and the browser harness could never make it succeed — it recorded the failure as an environment hazard ("no persona selected"). Continuing the host-write stage proved that diagnosis wrong: the failure is unconditional and caused by the capability itself. Total requirements 搂7 (host interaction) requires the declared write path to actually work.
- Stage: host write path, follow-up fix found while extending the harness.

## Root cause

`system_messages` in SillyTavern 1.19 is populated from templates and contains `help`, `welcome`, `empty`, `generic`, `slash_commands`, `hotkeys`, `formatting`, `macros`, `assistant_note` 鈥?but **not** `narrator` or `comment`, even though both exist in the type enum. `sendSystemMessage('narrator', 鈥?` therefore gets `undefined` from `getSystemMessageByType`, pushes it into `chat`, and throws inside `updateMessageElement` (`Cannot read properties of undefined (reading 'is_user')`).

The adapter's allowlist had been copied from the enum instead of the template map, so the **default type was a type the host cannot render**. Every plain `chat.append({ text })` failed; the previous recorded "no persona" explanation was wrong (selecting a persona does not help, verified by a diagnostic that set `powerUserSettings.personas` and retried).

## Changes

- `CHAT_MESSAGE_TYPES` 鈫?`['generic', 'assistant_note']`, `DEFAULT_CHAT_MESSAGE_TYPE = 'generic'`. The comment now says the allowlist follows the templates, not the enum, and names the reason.
- A rejected type is still `INVALID_INPUT` (schema enum), so `narrator`/`comment` fail before any host call instead of corrupting a chat and being rolled back.
- The append doc comment drops the claim that `narrator` is "for prose the reader should see".
- Browser harness:
  - `chat.append` is now verified for real on a **scratch character's chat** (default type, message appears, then edited and deleted again).
  - `probeChatWrite` no longer appends into whatever chat is open. It had started succeeding once the allowlist was fixed, and wrote a message into the **user's current chat** 鈥?a test must never do that. It now only checks the gate and that a denied call leaves the chat untouched, and records that the real write is covered by the scratch probe.
  - The one probe message that reached a user chat during this investigation was removed from the chat file (7 鈫?6 lines) with a backup taken first; no other user data was touched.

## Direct scope

`Loom Host/index.js`, `Loom Host/index.test.js`, `tests/browser/verify.mjs`, version markers, docs.

## Horizontal impact

- SYNC: unit tests now expect `type: 'generic'` and assert that `narrator` is rejected before the host is called; the rollback test uses `generic` so it still exercises a host that pushes an empty entry.
- SYNC: version markers 鈫?0.25.0.
- NO-CHANGE: `chat.edit`/`chat.delete` semantics; the rollback path; permission gating.
- **Harness safety rule added:** probes may only mutate data they created (scratch world books, scratch cards, scratch chats). Read-only assertions against live data are fine; writes into the user's chat or library are not.

## Validation

- `npm test`: **214 tests pass** (same count; expectations corrected).
- `npm run verify:browser`: **123/123 checks pass**, including: `chat.append` with its default type succeeds on the scratch chat; the appended message can be edited and deleted; the edit is persisted to the scratch chat's `.jsonl` file and the deletion removes it; a denied `chat.append` leaves the open chat at 5 messages; the scratch chat/card are removed afterwards and no `__loom*` leftovers remain.
- Diagnostic evidence for the root cause: direct `sendSystemMessage('narrator', 鈥?` throws `TypeError: Cannot read properties of undefined (reading 'is_user')` at `updateMessageElement`, the same with a persona selected; `system_messages` has no `narrator` key.

## Risks / outstanding

- Only `generic` and `assistant_note` are offered. A future host version that adds `narrator`/`comment` templates would need this allowlist updated 鈥?it is deliberately a list of known-good templates, not a capability probe (the adapter cannot inspect `system_messages` without host internals).
- `assistant_note` renders with assistant styling; it is offered for completeness, not as a narration channel.
- The harness now refuses to touch user chats, so a future host change that breaks appending can only be caught by the scratch-chat probe (which is a real end-to-end check).
