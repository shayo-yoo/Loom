# CHG-20261123-044

- Date: 2026-11-23 (Asia/Shanghai)
- Type: FEATURE, API, TEST, DOCS
- Requirement / motivation: the user asked whether other extensions could register their own capabilities in a partly unmanaged way — third-party expansion without a maintainer shipping every feature — and asked that such extensions be confirmed by the user at install time. Loom already allowed self-registration through the Core API, but nothing told the user it had happened.
- Stage: branch `feature/chat-paging-and-external`, second batch.

## Design

Three tiers are now distinguishable, and the distinction is carried by the runtime itself rather than by convention:

| Origin | How it appears | Who decided |
|---|---|---|
| `managed` | `extensions/<id>/` + index → loader | Loom's package list |
| `external` | calls `LoomUI.registerExternal` | the user, per extension |
| `direct` | bootstrap code (`registerExtension` directly) | the host/UI itself |

Core's extension record gained `origin`, validated against those three values (unknown strings are rejected, not coerced). The loader stamps `managed`; `registerExternal` stamps `external`; the bootstrap path keeps `direct`.

## The consent flow

1. Third-party code calls `LoomUI.registerExternal({ id, name, version?, author?, description?, permissions? })`.
2. The manifest is validated (identifier id, permission names, permissions must be an array — a malformed list fails loudly instead of being silently dropped, which would under-report to the user).
3. A record is persisted with `status: 'pending'` and a prompt appears with the name, id, version, author, description and the **declared permissions**.
4. Approve → the record becomes `approved` and Core registers it with `origin: 'external'`; its declared permissions become normal permission requests (the existing consent machinery, unchanged).
5. Deny → the record becomes `denied` and it is unregistered. A later request for the same id throws instead of re-prompting; the panel offers 改判允许 and 清除记录.
6. The decision is persisted (`loom-ui` state, `externalExtensions`), so a reload does not re-prompt, and boot only re-registers approved records.

`LoomUI` also exposes `approveExternal`, `denyExternal`, `removeExternal` and `listExternalExtensions` (rows joined with the live runtime state: `registered` is true only when the extension is actually active, and a failure carries its message).

## Boundary (stated, not implied)

This is a **cooperative gate, not a sandbox**: code that bypasses `registerExternal` and calls `SillyTavern`'s global Loom API directly is not stopped. That matches the project's stated scope (a local loader that protects the user from accidents, not from hostile code). The gate's value is UX and visibility: a well-behaved third party gets a real confirmation step, a persisted decision, and a row in the panel.

## Horizontal impact

- SYNC: `registerExtension` record shape changed (added `origin`); the Core test's deep-equal expectation was updated, and a new test covers all three origins plus rejection of an unknown one.
- SYNC: the panel gained a 第三方扩展 section and a floating consent card (`#loom_external_consent`), separate from the permission consent so a user answers registration before permissions.
- ADAPT: enabling a disabled package now unloads first and then imports unconditionally. The previous "skip if already active" optimisation made enabling depend on the loader record's state, which produced a row that was `disabled: false` but never registered — found by the browser probe, not by reading the code.
- ADAPT: the phone hit-test now hides any `[class*="dialogue_popup"]`/`.popup` overlay, because SillyTavern's dialog was leaving the page inert and every `elementFromPoint` returned HTML.
- NO-CHANGE: the permission model, capability execution, the loader's dependency ordering.

## Verification

- `npm test`: **270 tests pass** (+5 external-registry tests: normalisation and permission de-duplication, malformed manifests, pending-then-remembered decisions, status validation and forgetting, describing with live state).
- `npm run verify:browser`: **197/197 checks pass** (three consecutive runs). New: an external request stays **pending and unregistered** with the prompt visible; approving registers it with `origin: 'external'` and raises its permission request; denying keeps it out and a repeat request throws; clearing the record forgets it.

## Risks / outstanding

- The prompt has no timeout or queue limit: many simultaneous requests would stack in one card (readable, but not paginated).
- Approval registers the extension but does not pre-grant permissions — they still go through the normal request/consent path, which is intended but means two steps for a permissioned external extension.
- A denied record blocks the id until the user clears it; there is no "ask again" affordance from the extension's side.
- Bypassing the gate is possible by design (see Boundary).
