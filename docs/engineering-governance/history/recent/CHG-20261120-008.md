- Requirement / motivation: The Core requirements state that read and write capabilities must be declared separately and that Core must keep basic access constraints an ordinary extension cannot silently bypass (§5, §8), and the shared interface agreement requires data ownership, error feedback and lifecycle tracking to be explicit (§5, §7, §8). - Starting point (verified before editing): `git status` showed uncommitted changes in `Loom Core/index.js` and `Loom Host/index.js` only, with a single baseline commit (`a59a187`, 0.7.0). `npm test` failed 2 of 41 tests: the host capability-list assertion and the manifest/package version check. No change record, index or state entry described the in-flight work.

## Changes

### Core (`Loom Core/index.js`, runtime 0.7.0 → 0.8.0)

- Capabilities may declare `permissions: string[]`; names are validated (`/^[a-z0-9][a-z0-9._:-]*$/i`), duplicates collapse, the list is frozen, and it is exposed in capability descriptors.
- Added the grant table and `grantPermission` / `revokePermission` / `checkPermission` / `listPermissions`; grants are per extension, dropped on unregister, and counted by `getRuntimeInfo().grantedPermissionCount`.
- `executeCapability(extensionId, capabilityId, input, options?)` now takes `options.caller` (defaulting to the capability owner) and passes `{ caller, target, capabilityId, capabilityPermissions, hasPermission }` to the handler.
- **Corrected the in-flight design**: permissions were only *described* to the handler, so each capability had to remember to enforce them. Core now enforces declared permissions itself, in a fixed check order (ids → capability lookup → caller registration → input schema → permissions → handler → output schema), returning `PERMISSION_DENIED` with `details.missing`. A capability that forgets its own check can no longer run ungated.
- A thrown error carrying a string `code` keeps that code (and `details`) in the failure envelope, so adapters can return stable codes such as `HOST_UNAVAILABLE` instead of `EXECUTION_FAILED`.

### Host (`Loom Host/index.js`, 0.4.0 → 0.8.0, version now tracks the runtime)

- Added caller-scoped settings capabilities: `settings.get`, `settings.keys` (no grant) and `settings.set`, `settings.remove` (`host.settings.write`).
- **Corrected the in-flight design**:
  - Reads no longer create a namespace. The previous `callerSettingsRoot` wrote `extensionSettings[caller] = {}` on every read, so merely probing a key added empty objects to the user's persisted settings.
  - Removed the duplicated permission check inside the adapter; Core enforces it. The adapter keeps a separate `requireCaller` guard because the caller id is used as an object key (fails with `CALLER_REQUIRED`).
  - Added key hardening: 1–128 characters, `__proto__` / `prototype` / `constructor` rejected (prototype pollution), and values must be structured-cloneable.
  - The identity `content` fingerprint was stale (it listed four capabilities and omitted `viewport.get`); it is now derived from the capability list and its required permissions, so it cannot silently drift.
- Writes call `saveSettingsDebounced()`, giving extensions persisted storage for the first time.

### UI (`Loom UI/`)

- Added `permissions.js` (pure): `summarizePermissions`, `buildPermissionSectionHtml`, `countGranted`, `PERMISSION_SECTION_ID`, `PERMISSION_TOGGLE_CLASS`.
- Panel gained a permission section: each declared permission lists the capabilities requiring it plus one toggle per registered extension; toggling calls `grantPermission` / `revokePermission`. A single delegated listener is bound to the stable container so re-rendering cannot lose handlers.
- Panel shows an "已授权权限" count; capability entries list their declared permissions.
- Host capability calls now pass an explicit `{ caller: 'loom-ui' }`, so attribution does not silently become a self-call.
- Registered content fingerprint includes `permission-grants`.

### Versions

- `manifest.json`, `package.json` and the runtime are now all 0.8.0.

## Architecture / API / data

- New public API: permission grants and the `options.caller` argument. Both are additive; existing calls keep working because `caller` defaults to the capability owner and capabilities without declared permissions are unaffected.
- Data ownership: a capability can only write the caller's own `extensionSettings` namespace, which satisfies "不能默认一个组件拥有修改其读取到的全部数据的权限".
- Error contract: added `CALLER_NOT_FOUND`, `PERMISSION_DENIED`, `CALLER_REQUIRED`, `HOST_UNAVAILABLE`, and typed-error passthrough.

## Compatibility / migration

Additive. No capability ids, event names, component ids or state keys were removed or renamed. Capabilities that declare no permissions behave exactly as before. The one behavioural change: a call from an unregistered caller now fails with `CALLER_NOT_FOUND` instead of executing — no existing caller relied on that.

## Failed checks and corrections (recorded, none hidden)

1. The in-flight permission model delegated enforcement to each handler; Core now enforces centrally.
2. The in-flight settings reads created empty namespaces in the user's persisted settings; fixed with a `create` flag.
3. A first edit replaced `const result = await runtime.executeCapability(...)` with a `void` call, which would have broken `refreshHostSnapshot`; noticed immediately from the surrounding code and reverted before running anything.
4. A new UI test asserted an empty summary for a fixture that does declare permissions; the fixture was wrong, the assertion was corrected (the implementation was not changed to fit the test).
5. A holder-order expectation assumed input order; holders are sorted by extension id (`named` < `nameless`). Expectation corrected.
6. `git diff` warns that LF will be replaced by CRLF; the repository already has mixed line endings and `.gitignore` does not address it. Not changed here.

## Risks / outstanding

- Grants are session-scoped and there is no consent prompt or policy store; a reload clears every grant, so `settings.set` needs re-granting. Persisting the grant policy is the natural next step and needs a decision about where the policy lives (Core state vs host settings vs the UI's own namespace).
- Permissions are not a security boundary. Any script in the page can call `grantPermission` for itself or bypass Loom via `SillyTavern.getContext()`. This is documented in `API_INDEX.md` rather than papered over; a real boundary would need realm isolation, which SillyTavern extensions cannot provide.
- The caller identity is self-declared: a script can pass `options.caller` with another extension's id. Fine for attribution and accident prevention, not for authorization between hostile parties.
- `extensionSettings[caller]` shares a flat namespace with other SillyTavern extensions. Collisions are unlikely (Loom ids are hyphenated) but not enforced; a reserved root key would need a migration decision.
- Browser verification of 0.8.0 is outstanding.
