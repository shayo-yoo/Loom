# CHG-20261124-050

- Date: 2026-11-24 (Asia/Shanghai)
- Type: FEATURE, TEST, DOCS
- Requirement / motivation: the user's scenario review found one real gap across two use cases — quick replies and panel choices could not actually reach the model. `chat.append` writes system messages only, so nothing could put text in front of the user or speak as the user. This round closes exactly that gap and nothing else.
- Stage: branch `feature/chat-send`, version 0.42.0.

## Design

Two capabilities, split by risk rather than convenience:

| Capability | Effect | Permission |
|---|---|---|
| `chat.input.set` | writes the composer (`#send_textarea`); no message, no save | `host.chat.write` |
| `chat.send` | writes a **user turn** (render + save), optionally starts a generation | `host.chat.send` (new) |

Splitting them matters: drafting is reversible and cheap; speaking as the user can spend tokens and cannot be unsaid. An extension that may prefill a quick reply should not thereby gain the right to press send.

## Implementation notes

- **Composer.** Setting `.value` is not enough — SillyTavern drives its send-button state from the `input` event, so the adapter dispatches one after writing. The returned `text` is read **back from the element**, not echoed, so a host that rewrites the value is reported honestly. `mode: 'append'` concatenates; `replace` is the default.
- **User turn.** `context.addOneMessage` expects the caller to have pushed the message first ("Callers push the new message to chat before calling addOneMessage"), so the handler builds `{ name, is_user, is_system: false, send_date, mes, extra }`, pushes, renders, then `saveChat()`. `send_date` is an ISO string, which is what `getMessageTimeStamp()` returns.
- **Macros, not regexes.** `{{user}}`-style macros go through `context.substituteParams` when it exists. The host's user-input regex is **not** applied: `getRegexedString` is not exposed by `getContext()`. The difference is documented rather than approximated.
- **Generation is opt-in.** `generate: true` starts it; `wait: true` makes the call resolve after the reply (`generationCompleted: true`), otherwise it returns immediately with `generationStarted: true` and a logged failure. The hook is checked **before** writing, so a request that cannot be honoured leaves no message behind.
- **Rollback.** A render failure removes the pushed message and reports `HOST_UNSUPPORTED`, matching `chat.append`: the user must never see a message they did not type.

## Verification

- `npm test`: **306 tests pass** (+6: composer write/append/read-back, gating and missing composer, user turn with macro expansion and persistence, generation fire-and-forget vs awaited, render-failure rollback, gating/NO_CHAT/generate-hook-checked-first).
- `npm run verify:browser`: **220/220 checks pass**, three consecutive runs. New probes run inside the scratch character's chat: `chat.send` adds exactly one user message with macros expanded and the text appears in the chat `.jsonl`; `chat.input.set` fills and appends to the composer without sending, then restores the original value.

## Deliberate gap (recorded)

The **real generation path is not exercised in the browser harness.** Two reasons, both concrete:

1. It would call a real model API — cost and credentials, which a verification run must not require.
2. `getContext()` returns a fresh object per call, so the harness cannot monkey-patch `generate` on it: the first attempt did exactly that, the stub was ignored, a real request ran, and it returned a 502 that the console-error check caught.

Coverage split: unit tests own the generate wiring (stub host, both `wait` modes); the browser probe owns "writes one user turn, expands macros, persists, no generation by default".

## Known gaps

- No `chat.stop` / abort, and no way to observe an in-flight generation from a capability.
- `chat.send` cannot target a specific message index (append only); inserting into the middle still needs `chat.edit` plus an insert-style capability that does not exist.
- The user-turn regex gap above; if a future host exposes `getRegexedString`, applying it should become the default.
