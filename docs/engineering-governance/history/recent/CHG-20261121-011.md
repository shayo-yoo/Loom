# CHG-20261121-011

- Date: 2026-11-21 (Asia/Shanghai)
- Type: FEATURE, API, TEST, DOCS, ARCH
- Requirement / motivation: Core requirements §5 requires read and write capabilities to be declared separately and forbids treating read data as writable by default; the total requirements §7 names "使用 Loom UI 编辑和提交世界书数据" as the canonical host-interaction example. CHG-20261121-010 delivered the read side and recorded the write side as deliberately deferred until a merge contract existed. This change defines that contract and ships the first write capability, so the read-only adapter is no longer a dead end for the world-book flow.
- Stage: first increment of the write-back stage.

## Design decision: entry-level patch, not whole-book write

`saveWorldInfo(name, data, immediately)` takes a whole book. Exposing it directly would let any caller replace an entire world book from a snapshot it read minutes ago, silently discarding concurrent edits — exactly the "默认拥有修改其读取到的全部数据的权限" the requirements forbid.

Chosen contract instead:

1. The caller supplies `{ name, uid, patch }`; it patches fields, never a whole book.
2. The adapter re-reads the book, applies the patch to the matched entry, and saves immediately (`immediately = true`), so a resolved success means SillyTavern accepted the write instead of queueing a debounce that could be lost on navigation.
3. Last write wins. No revision token exists yet; recorded as a known limit rather than implied as a guarantee.
4. Unknown patch fields fail with `INVALID_INPUT` instead of being ignored, so a typo cannot silently no-op while the caller believes it edited something.
5. `enabled` maps onto SillyTavern's inverted `disable` flag; fields outside the patch are untouched.
6. An empty patch returns `updated: []` and does not touch the book or issue a save.

## Changes

### Host (`Loom Host/index.js`, 0.10.0 → 0.11.0)

- Added `worlds.entry.update` with input `{ name, uid, patch }` and output `{ name, uid, updated }`. Permitted patch fields: `content`, `comment`, `keys`, `secondaryKeys`, `enabled`, `constant`, `selective`, `order`.
- Gated behind **`host.worldinfo.write`**, declared on the capability so Core enforces it centrally.
- New structured failures: `WORLD_NOT_FOUND`, `ENTRY_NOT_FOUND`, and `HOST_UNSUPPORTED` when the host does not expose `loadWorldInfo`/`saveWorldInfo`.
- The capability list and the derived content fingerprint pick the new capability up automatically.

### Versions

- Core `LOOM_VERSION`, Host `HOST_VERSION`, `manifest.json`, `package.json` → 0.11.0.

## Architecture / API / data

- One new write capability and one new permission name (`host.worldinfo.write`).
- Three new error codes: `WORLD_NOT_FOUND`, `ENTRY_NOT_FOUND`, `HOST_UNSUPPORTED`.
- Write path never returns the mutated entry, only the list of updated field names: that keeps the response small and forces a caller that wants to render the result to re-read through `worlds.entries`, which is the same shape UI consumers already use.

## Compatibility / migration

Additive. No existing capability changed. Installs gain one grantable permission; until it is granted, `worlds.entry.update` fails with `PERMISSION_DENIED` and the panel shows the toggle.

## Validation

- `npm test`: **pass, 83 tests** (was 78). New coverage: read-modify-write through a stubbed book asserting mutated fields, untouched fields, inverted `disable`, `updated` list and `immediately: true`; denial without the grant leaving the book unmodified and saving nothing; `ENTRY_NOT_FOUND` and `WORLD_NOT_FOUND`; unknown patch field rejected by the schema with the book unchanged; empty patch returning `updated: []` without a save; `HOST_UNSUPPORTED` when `saveWorldInfo` is absent.

## Failed checks and corrections (recorded, none hidden)

1. The capability-list assertion failed after adding the capability; updated to the new contract, not loosened.
2. Initially considered exposing `saveWorldInfo` directly with a whole-book payload. Rejected during design review: it allows silent clobbering of concurrent edits and breaks the "cannot modify everything it can read" rule. The rejection and its reason are recorded here.
3. A doc edit temporarily split the host capability tables and left the settings rules dangling after the write section. Restructured in place; the file was re-read to confirm the final order.

## Risks / outstanding

- Last-write-wins with no revision token: two editors patching different fields of the same entry can still lose an update if both read before either writes.
- `loadWorldInfo` returns a cached book; a write goes through the same cache, so the adapter and other ST surfaces stay consistent, but an external file change outside ST is not detected.
- Only update exists — no create, delete or rename, and no bulk operations. Each needs its own contract (uid allocation, cascade rules) before being exposed.
- Chat injection and character-card editing are still read-only; they need the same treatment.
- Browser verification of 0.11.0 is outstanding.
