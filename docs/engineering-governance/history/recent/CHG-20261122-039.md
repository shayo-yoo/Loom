# CHG-20261122-039

- Date: 2026-11-22 (Asia/Shanghai)
- Type: FEATURE, API, DATA, TEST, DOCS
- Requirement / motivation: the requirements review found four contract gaps — package identity had no author, the content hash covered only a self-declared string, interfaces could not describe their errors or compatibility, and data types had no identity at all. These are the "A-class" items agreed as the next stage; visual editing stays an extension.
- Stage: branch `feature/identity-and-contract-gaps`, first batch.

## Package identity: author

- `extensions/*/manifest.json` gains an optional `author`; the index generator validates it as an identifier and emits it, and both bundled packages declare `author: "loom"`.
- The loader already passed `author` through; packages previously arrived as `anonymous:<id>`. Identity is now `loom:hello-loom` etc., and the panel row shows the author.
- An invalid author (spaces, punctuation) fails indexing with a concrete message instead of silently becoming anonymous.

## Content hash: actual package content

- `npm run extensions:index` now hashes `JSON.stringify({ author, dependencies, description, entry, id, name, permissions, version, source })`, where `source` is the entry module's text, using the same FNV-1a 64 algorithm as Core (UTF-16 code units, `fnv1a64:` prefix).
- The index carries `contentHash`; the installer passes it into `importExtension` as manifest metadata; the loader forwards `contentHash` to Core, so `identityKey`/`contentHash` describe the real package rather than a declared string.
- A test proves the hash tracks entry edits and stays stable across regeneration.

## Interface metadata: errors and compatibility

Capability descriptors accept two optional fields, validated in Core:

- `errors`: array of `{ code: UPPER_SNAKE_CASE, description? }`, for the "possible errors" the interface contract asks an interface to describe.
- `compatibility`: `{ since?, deprecated?, notes? }`; unknown fields are rejected.

Both are cloned into `listCapabilities()` snapshots. They are metadata for callers/tooling; Core does not enforce that a handler only fails with declared codes (recorded as intentional).

## Data types: stable identity

- New Core registry: `registerType(extensionId, { id, name, description?, schema? })`, `getType(extensionId, id)`, `listTypes(extensionId?)`. Identity is `extensionId:typeId`; the schema is validated with the same subset checker as capabilities but never interpreted at runtime.
- Types are removed when their extension unregisters (verified), and `getRuntimeInfo().typeCount` exposes the count.
- This is deliberately a naming/contract registry, not a type system: it lets an interface say "I exchange `ext:note`" without Core understanding notes.

## Direct scope

`Loom Core/index.js`, `Loom Core/index.test.js`, `Loom Core/loader.js`, `scripts/extensions-index.mjs`, `tests/extensions-index.test.js`, `Loom UI/installer.js`, `Loom UI/index.js`, package manifests, `extensions/index.json`, `tests/browser/verify.mjs`, docs, version markers.

## Horizontal impact

- SYNC: `normalizeIndex` carries `author`/`contentHash`; `describeInstalled` gained `author`; the panel row shows it.
- SYNC: the loader passes `contentHash`; Core's `resolveContentHash` already accepted a supplied hash, so no algorithm change was needed.
- ADAPT: the browser probe registers a temporary `verify-metadata` extension, asserts the declarations and the type lifecycle, then unregisters it — it must not reuse `verify-probe`, whose registration other probes assume.
- NO-CHANGE: capability execution, permissions, UI rendering; the script path now passes its source as `content`, so scripts also get a real hash.

## Verification

- `npm test`: **253 tests pass** (+7: capability metadata, validation, type registry/lifecycle, index author/hash).
- `npm run verify:browser`: **185/185 checks pass**. New: `hello-loom` registers `author: "loom"`, `identityKey: "loom:hello-loom"` and a `fnv1a64:` hash from the index; a capability's declared errors/compatibility appear in `listCapabilities`; a type registers, resolves by identity, and disappears with its owner.

## Risks / outstanding

- The hash covers the manifest and the entry file only: additional files a package might load at runtime are not represented. Multi-file packages would need the generator to walk the entry's imports, which is not implemented.
- Authors are self-declared identifiers, not verified accounts (out of scope per the requirements).
- `errors` declarations are advisory: a handler can still return any runtime code, and the panel/consent UI does not yet render them.
- Type identities are names, not structural contracts; nothing checks that two interfaces describing the same type mean the same fields.
