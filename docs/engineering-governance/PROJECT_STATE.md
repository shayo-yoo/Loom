# Project State

## Confirmed Baseline

- Loom is a framework project intended to run as an extension in SillyTavern.
- The workspace initially contained only the total requirements, Core requirements, UI requirements, shared interface agreement, and `AGENTS.md`.
- SillyTavern checkout: `D:\1\APP\SillyTavern`, version 1.19.0.
- SillyTavern's existing third-party extension loader discovers manifests under `public/scripts/extensions/third-party`.
- ST `config.yaml` declares port 8100, but no process was listening on 8100 during the first implementation attempt. A previous `.st-run.log` recorded an invocation on port 8000.
- The ST checkout had pre-existing user changes in `Start.bat`, `.st-run.log`, and `酒馆.bat`; these were not modified.

## Current Objective

Deliver an initial Loom runtime and UI extension that can be discovered and enabled through SillyTavern, then iterate toward the framework requirements without embedding business-specific behavior in Core.

## Current Implementation

- Core exposes a small in-memory extension/capability registry, JSON Schema subset validation for declared inputs/outputs, structured execution results, an extension-scoped event bus, per-extension state storage (optionally persisted), disposal hooks, and extension-scoped cleanup (runtime 0.19.0).
- Core implements extension identity: `author + declaredId`, deterministic `contentHash` (FNV-1a 64), install pre-checks (`new` / `duplicate` / `conflict`), and identity-group conflict reporting.
- Core implements capability permissions: capabilities declare the permissions their caller must hold, `executeCapability` takes an explicit `caller`, and Core enforces the grants centrally before the handler runs (`PERMISSION_DENIED` with `details.missing`). Grant/revoke/list/check are public API; grants are per extension and dropped on unregister.
- Core exposes `setPermissionStore({ load, save })` so a host can persist the grant table. `Loom Host` installs one backed by SillyTavern settings (`extensionSettings.__loom.grants`), so consent survives a reload; pending grants apply when their extension registers, making boot order irrelevant.
- Core implements a permission consent flow: `requestPermission` opens a prompt (emitting `core:permission:requested`), `resolvePermissionRequest` grants or denies it, and `listPermissionRequests` exposes the queue. Requests de-duplicate per extension+permission and are dropped when the extension unregisters.
- `Loom UI` renders that consent prompt in `#loom_consent` through its own view engine (`LoomUI.createView`), which makes the UI system a consumer of the framework instead of hand-written markup everywhere.
- Since 0.14.0 `Loom Core/loader.js` adds manifest-driven loading, and since 0.17.0 `startExtensions()` boots every loaded extension in dependency order and `importExtension(url)` loads a module's manifest. `loom-host` and `loom-ui` remain `unmanaged` (they register directly during bootstrap); an `unmanaged` extension satisfies a dependency because its setup already ran.
- `Loom Host` is an independent SillyTavern adapter registering read capabilities (`context.snapshot`, `characters.list`, `characters.get`, `worlds.list`, `worlds.entries`, `worlds.export`, `chat.messages`, `viewport.get`), write capabilities (`settings.get`/`keys`/`set`/`remove`, `worlds.create`/`remove`/`import`/`rename`, `worlds.entry.update`/`create`/`remove`, `chat.append`) and bridging 7 allowlisted host events as `host:*` Loom events. Writes require `host.settings.write` / `host.worldinfo.write` / `host.worldinfo.manage` / `host.chat.write`; reading chat content requires `host.chat.read`.
- `Loom UI` provides a generic interface system: an extension-owned component registry with 16 built-in components (`text`, `button`, `input`, `toggle`, `select`, `card`, `row`, `column`, `grid`, `divider`, `list`, `badge`, `image`, `tabs`, `modal`, `menu`), a pure view-tree validator/mutator with serialization, and a DOM view engine that supports create, update (in place via component `update`), append, remove, describe, serialize and destroy, preserving focus/selection/scroll across structural rebuilds. Exposed as `globalThis.LoomUI` and as `ui.components` / `ui.views` capabilities.
- Core has a manifest-driven extension loader (`Loom Core/loader.js`): `loadExtension` registers identity only, `activateExtension` checks dependencies, requests declared permissions and runs the activation hook, `deactivateExtension`/`unloadExtension` close the lifecycle, failures are recorded as extension state instead of thrown, and the panel lists every extension's state (including `unmanaged` bootstrap registrations). `startExtensions()` boots every loaded extension in dependency order; `importExtension(url)` loads a module's manifest and activates it, reporting import/manifest problems as structured failures.
- Consent prompts show, per requested permission, the declaring capability and a one-line input → output contract summary (`describeContract`), so a grant decision is informed rather than blind.
- Loom has two SillyTavern entries: the wand menu launcher and an inline drawer in the extension settings panel (`#loom_settings_entry`), both opening the same panel.
- UI loads Core and the host adapter, registers itself, shows runtime counts, live host snapshot, viewport size, event listeners, capability contracts, declared permissions with grant toggles, UI component/view summary and identity conflicts, and auto-refreshes on host events.
- The Loom repository root contains the ST extension manifest. ST is intended to reference the workspace through a directory junction so there is one source of truth.

## Open Work / Risks

- Runtime 0.22.0 is verified in a real browser: `npm run verify:browser` drives headless Chrome over the DevTools protocol against SillyTavern on port 8100 and passes 107 checks. Unit tests: 203 passing. Coverage includes extension state surviving a real page reload, a dynamically imported extension module, dependency-ordered startup, consent prompts with contract summaries, keyed reconciliation keeping elements and focus, controlled `tabs`/`modal`, `chat.append`'s gate and rollback, and the whole world-book lifecycle including export/import round-trips and a rename that migrates chat/persona bindings and refuses unsafe references. A human visual review of layout still only exists for 0.7.0.
- Manifests are discovered only by the host: there is no on-disk scan, and `importExtension` trusts the module's declared id. Dynamically imported module code cannot be unloaded from the browser module registry, so "reinstall" means a new page load.
- The consent prompt has no memory: a denial is not recorded, so an extension that re-requests will prompt again. There is also no per-extension "always allow" option beyond the panel toggle.
- Host coverage is still partial: no chat pagination cursor, no world-book rename when a character card is bound, no bulk operations, and world-entry writes are last-write-wins without revision tokens. `chat.append` writes system messages only; user/character messages and character-card editing remain read-only.
- SillyTavern's in-memory world cache cannot be evicted for a deleted book (no delete function is exposed), so reads immediately after `worlds.remove` may return cached data until reload. Writes go through `saveWorldInfo` to keep the cache correct for create/import/rename.
- `worlds.rename` refuses when a character card points at the book or it is globally activated (`WORLD_IN_USE`) rather than renaming and breaking the reference; card links need card writing and the activation dropdown belongs to the host. Chat and persona bindings are migrated.
- World books can be exported (raw host data, detached) and imported into a new name; import never overwrites, and validates entry shape/size before writing.
- `worlds.remove` is irreversible: protection is the separate `host.worldinfo.manage` permission, the consent prompt and the `confirm` echo — there is no soft delete, backup or undo, and no dedicated UI confirmation dialog (recorded as an open product question).
- World-book creation and deletion call SillyTavern's `/api/worldinfo/{edit,delete}` endpoints because `getContext()` exposes no equivalent; a host release that moves those endpoints would break those two capabilities (reads are unaffected).
- `chat.append`'s success branch is verified by a one-off manual diagnostic (a clean chat accepts a `generic` system message), not by the standing browser harness: the headless session's chat contained a malformed entry, on which SillyTavern's own renderer throws. The harness asserts the gate and the rollback instead, and records the boundary.
- The world entry defaults mirror SillyTavern 1.19.0's `newWorldInfoEntryTemplate`; a host upgrade that changes the entry model must update `WORLD_ENTRY_DEFAULTS` in `Loom Host/index.js` or new entries will be missing fields.
- Identity fingerprints are non-cryptographic (`fnv1a64`) and supplied or derived from registrant-provided content; they are not signatures and do not prove authorship or integrity. No online trust/registry, install gate in the ST loader, or migration flow yet.
- Permissions are an access constraint, not a sandbox: all scripts share the page realm, so a hostile script can grant itself permissions or bypass Loom entirely via `SillyTavern.getContext()`. There is no consent prompt yet — a user must open the panel and toggle a grant — and the caller identity is self-declared.
- Core state is per-extension and persisted when a store is attached (`setStateStore`); the host stores snapshots under `extensionSettings.__loom.state[extensionId]`, so state survives a reload. Only `structuredClone`-able values are persisted; live values stay in memory and are skipped. Events remain page-scoped by design. State sharing still requires exposing a capability.
- No cross-extension version/compatibility negotiation yet.
- UI system: `setProps` updates in place, `setChildren` reconciles children by `key` (or index + component) so matched items keep their element, listeners and state, and only `setRoot` rebuilds a whole tree. Serialization round-trips (handlers stripped, keys kept). `modal` and `tabs` are controlled components: interaction reports intent, the declared props decide the visible state. Remaining gaps: no virtualisation, no handler-closure rebinding beyond the node's current `on`, and moved items lose element-level scroll positions.
- Manifests are JavaScript objects passed in code; there is no file discovery, no dependency version constraints, and loader state is in memory (every reload starts at `loaded`).
- Mobile support is currently "mobile-safe, not mobile-optimized": layouts are fluid, tap targets are ≥44px, safe-area insets are respected, grids collapse at ≤768px, and `viewport.get` exposes width/isMobile. Not yet covered: touch gestures (swipe/drag/long-press), on-screen keyboard viewport changes, virtualized long lists, and dedicated phone layouts for dense panels.
- Do not express breakpoints through CSS custom properties inside media queries (browsers ignore them); use literal values and keep them documented.
- Host events carry only `{ source, event }` and never host payloads. Chat message contents and user settings are not exposed.
- `characters.list` and `worlds.list` return complete lists with no pagination; large libraries render slowly in UI-driven consumers.
- In-page extension unload does not exist in SillyTavern, so cleanup runs on explicit unregister or page reload.
- SillyTavern has existing user modifications; avoid modifying or reverting them.
