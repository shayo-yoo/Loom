# Project State

## Confirmed Baseline

- Loom is a framework project intended to run as an extension in SillyTavern.
- The workspace initially contained only the total requirements, Core requirements, UI requirements, shared interface agreement, and `AGENTS.md`.
- SillyTavern checkout: `D:\1\APP\SillyTavern`, version 1.19.0.
- SillyTavern's existing third-party extension loader discovers manifests under `public/scripts/extensions/third-party`.
- ST `config.yaml` declares port 8100, but no process was listening on 8100 during the first implementation attempt. A previous `.st-run.log` recorded an invocation on port 8000.
- The ST checkout had pre-existing user changes in `Start.bat`, `.st-run.log`, and `酒馆.bat`; these were not modified.

## Current Objective

Deliver an initial Loom runtime and UI extension that can be discovered and enabled through SillyTavern, then iterate toward the framework requirements without embedding business-specific behavior in Core.

## Increment Report Convention

Every completed increment ends with a short status overview for the user, in this shape (keep it factual, no promises):

1. **Current position**  - what Loom is right now, in one or two sentences (framework vs. usable product).
2. **What an extension author can already do**  - concrete capabilities, permissions, and a plausible extension idea they enable.
3. **What is still missing before real use**  - ordered gaps (P0 blocks use, P1 blocks real workflows, P2 polish) with a rough size.
4. **Verification evidence**  - unit test count, browser check count, and what the browser harness actually touched.
5. **Known limits / incidents**  - anything the user must know (data touched, unverified paths, environment limits).

The summary is delivered in the conversation; the change record stays a technical document. If a session resumes without this history, reconstruct the summary from `PROJECT_STATE.md`, `API_INDEX.md` and the latest `CHG-*` files rather than guessing.

## Current Implementation

- Core exposes a small in-memory extension/capability registry, JSON Schema subset validation for declared inputs/outputs, structured execution results, an extension-scoped event bus, per-extension state storage (optionally persisted), disposal hooks, and extension-scoped cleanup (runtime 0.27.0).
- Core implements extension identity: `author + declaredId`, deterministic `contentHash` (FNV-1a 64), install pre-checks (`new` / `duplicate` / `conflict`), and identity-group conflict reporting.
- Core implements capability permissions: capabilities declare the permissions their caller must hold, `executeCapability` takes an explicit `caller`, and Core enforces the grants centrally before the handler runs (`PERMISSION_DENIED` with `details.missing`). Grant/revoke/list/check are public API; grants are per extension and dropped on unregister.
- Core exposes `setPermissionStore({ load, save })` so a host can persist the grant table. `Loom Host` installs one backed by SillyTavern settings (`extensionSettings.__loom.grants`), so consent survives a reload; pending grants apply when their extension registers, making boot order irrelevant.
- Core implements a permission consent flow: `requestPermission` opens a prompt (emitting `core:permission:requested`), `resolvePermissionRequest` grants or denies it, and `listPermissionRequests` exposes the queue. Requests de-duplicate per extension+permission and are dropped when the extension unregisters.
- `Loom UI` renders that consent prompt in `#loom_consent` through its own view engine (`LoomUI.createView`), which makes the UI system a consumer of the framework instead of hand-written markup everywhere.
- Since 0.14.0 `Loom Core/loader.js` adds manifest-driven loading, and since 0.17.0 `startExtensions()` boots every loaded extension in dependency order and `importExtension(url)` loads a module's manifest. `loom-host` and `loom-ui` remain `unmanaged` (they register directly during bootstrap); an `unmanaged` extension satisfies a dependency because its setup already ran.
- `Loom Host` is an independent SillyTavern adapter registering read capabilities (`context.snapshot`, `characters.list`, `characters.get`, `worlds.list`, `worlds.entries`, `worlds.export`, `chat.messages`, `viewport.get`), write capabilities (`settings.get`/`keys`/`set`/`remove`, `worlds.create`/`remove`/`import`/`rename`, `worlds.entry.update`/`create`/`remove`, `characters.update`/`create`/`remove`, `chat.append`/`edit`/`delete`, `prompt.set`/`clear`/`list`) and three registration origins (`managed`, `external`, `direct`) and bridging 7 allowlisted host events as `host:*` Loom events. Writes require `host.settings.write` / `host.worldinfo.write` / `host.worldinfo.manage` / `host.characters.write` / `host.characters.manage` / `host.chat.write` / `host.prompt.inject`; reading chat content requires `host.chat.read`.
- Since 0.26.0 Loom installs extensions: bundled packages under `extensions/<id>/` are indexed by `npm run extensions:index` into `extensions/index.json` and loaded at boot, while user-installed module URLs are remembered in the UI's persisted state (`LoomUI.installExtension`/`uninstallExtension`). The panel has an install section listing every package with its state and errors. `extensions/hello-loom` is the minimal reference package (`hello.greet`); `extensions/world-book-manager` is the user-visible product demo (browse books, edit an entry's content/comment/enabled through a LoomUI panel, real save results). `docs/guides/writing-an-extension.md` is the developer guide.
- `Loom UI` provides a generic interface system: an extension-owned component registry with 17 built-in components (`text`, `button`, `input`, `textarea`, `toggle`, `select`, `card`, `row`, `column`, `grid`, `divider`, `list`, `badge`, `image`, `tabs`, `modal`, `menu`), a pure view-tree validator/mutator with serialization, and a DOM view engine that supports create, update (in place via component `update`), append, remove, describe, serialize and destroy, preserving focus/selection/scroll across structural rebuilds. Exposed as `globalThis.LoomUI` and as `ui.components` / `ui.views` capabilities.
- Core has a manifest-driven extension loader (`Loom Core/loader.js`): `loadExtension` registers identity only, `activateExtension` checks dependencies, requests declared permissions and runs the activation hook, `deactivateExtension`/`unloadExtension` close the lifecycle, failures are recorded as extension state instead of thrown, and the panel lists every extension's state (including `unmanaged` bootstrap registrations). `startExtensions()` boots every loaded extension in dependency order; `importExtension(url)` loads a module's manifest and activates it, reporting import/manifest problems as structured failures.
- Consent prompts show, per requested permission, the declaring capability and a one-line input → output contract summary (`describeContract`), so a grant decision is informed rather than blind.
- Loom has two SillyTavern entries: the wand menu launcher and an inline drawer in the extension settings panel (`#loom_settings_entry`), both opening the same panel.
- UI loads Core and the host adapter, registers itself, shows runtime counts, live host snapshot, viewport size, event listeners, capability contracts, declared permissions with grant toggles, UI component/view summary and identity conflicts, and auto-refreshes on host events.
- The Loom repository root contains the ST extension manifest. ST is intended to reference the workspace through a directory junction so there is one source of truth.

## Open Work / Risks

- Runtime 0.40.0 is verified in a real browser: `npm run verify:browser` drives headless Chrome over the DevTools protocol against SillyTavern on port 8100 and passes 215 checks. Unit tests: 300 passing. Coverage includes the bundled index, `hello-loom` activation, a user install persisted across a real page reload, disabling a package and boot skipping it (persisted across a reload), reloading a package, a pasted script that registers a capability, survives a reload, can be disabled/enabled and is deleted, the world-book manager paging/searching a twelve-entry book and saving through its own DOM, Loom button layout (no `min-content` collapse), a 390px phone pass that asserts the panel is full-height and hit-testable, character card creation/deletion on disk (including the retained chat directory), a rename that rewrites a bound card's `extensions.world` on request, extension state surviving a reload, dependency-ordered startup, consent prompts with contract summaries (scoped per request), keyed reconciliation keeping elements and focus, controlled `tabs`/`modal`, `chat.append`/`edit`/`delete` on a scratch character's chat (including the `.jsonl` on disk), `characters.update` (including the PNG's V2 `data` block), and the whole world-book lifecycle including export/import round-trips. A human visual review of layout still only exists for 0.7.0; the mobile pass is synthetic (CDP emulation), not a real device.
- Manifests are discovered only by the host: there is no on-disk scan, and `importExtension` trusts the module's declared id. Dynamically imported module code cannot be unloaded from the browser module registry, so disabling is logical and a page reload is the only physical reset.
- Scripts are module source stored in SillyTavern settings and re-run on boot when enabled; they share the extension trust boundary and are not sandboxed. A disabled script stays in the list, and a very large script bloats the settings payload.
- Third-party code can register itself through `LoomUI.registerExternal`, which shows a prompt and persists the user's decision (`external` origin). This is a cooperative gate, not a sandbox: bypassing it and calling the global runtime directly is not prevented — consistent with the project's "local loader, not hostile-code boundary" scope.
- `chat.messages` pages by absolute index and can search the text, but there is no revision token: a message inserted between two pages shifts the window.
- A block only shows if a marker is written into a message, and writing is a visible side effect: `character-panel` adds its panel through `panel.show` plus a wand-menu entry, never on activation. Activation only draws a marker that already exists.
- Interaction with a rendered widget requires `rerenderBlocks`: the marker is gone after the first render, so a text-based refresh finds nothing.
- Imported packages are cache-busted with their content hash; without it an edited extension kept running the previously cached module and looked "unchanged".
- `extensions/character-panel` is the validation sample for the whole loop: a block panel in the message, a natural-language state injection with receipt rules, and `[[item:…]]` receipts that change the panel. It needs `host.prompt.inject` and `host.chat.read` approved, and it seeds the existing messages as processed at activation so a reload cannot replay history.
- Interactive block rendering belongs to Loom UI (CHG-046): `registerBlock` defines a widget kind, `refreshBlocks` renders blocks found in message text. Only the visual creator and concrete widget sets are extensions. There is no viewport-based lazy mounting yet, and clicking inside a message still competes with SillyTavern's own handlers.
- Display-only blocks (the marker form loom:kind wrapped in U+27E6/U+27E7) are stripped from the prompt by the host adapter on both prompt families, so a UI can be rendered in a message without the model reading it. Nothing renders blocks yet, and the markers persist in the chat file (visible in exports) — the price of surviving re-renders.
- Loom does not ship a regex engine: arbitrary text hiding stays with SillyTavern regex extension, whose markdownOnly and promptOnly flags already mean "display only" and "prompt only". That rule is user-written and user-visible, and SillyTavern does not expose getRegexedString through getContext(), so calling it would mean importing host internals.
- Prompt injection is supported (`prompt.set`/`clear`/`list`) but generation-time mutation is not: SillyTavern's `GENERATION_AFTER_COMMANDS` options object is undocumented internals, so wrapping it would be a fragile contract. Injected text becomes part of the user's prompt and no UI shows the user what an extension injected (`prompt.list` is caller-scoped by design).
- Views can be mounted into four SillyTavern containers (`#extensions_settings`, `#extensions_settings2`, `#extensionsMenu`, `#left-nav-panel`) through `LoomUI.mountToSlot`. The list is an allowlist bound to host 1.19 markup; a rename degrades to "nothing renders" rather than throwing.
- Mobile: the phone panel previously collapsed to zero height because SillyTavern's transformed, zero-height root broke `position: fixed; inset: 0`; Loom now states `100vh/100dvh` and the manager anchors from the top. The harness asserts panel height, top, hit-testability and manager bounds at 390×844. Real devices, soft-keyboard viewport changes, touch gestures and long-list virtualisation remain untested; the page's own baseline overflow at that width comes from other SillyTavern extensions and is outside Loom's control.
- The consent prompt has no memory: a denial is not recorded, so an extension that re-requests will prompt again. There is also no per-extension "always allow" option beyond the panel toggle.
- Extension discovery is index-based: `extensions/index.json` is generated and committed, so a package added without running `npm run extensions:index` stays invisible. There is no watcher or pre-commit hook; enabling/disabling and reloading are supported from the panel.
- Manually installed extensions are fetched from arbitrary module URLs on every boot (code execution at the user's request) with no integrity check; the identity fingerprint detects duplicate/conflict, not maliciousness. A failed import keeps its record so the error stays visible, and recovery is manual.
- Host coverage is still partial: no chat pagination cursor, no bulk operations, and world-entry writes are last-write-wins without revision tokens. `worlds.entries` pages and searches (200-entry page limit, linear in-memory scan) but there is no cursor or indexed search. `worlds.rename` can move bound card links on request but an embedded `character_book` copy still blocks. `chat.append` writes system messages only; user/character messages remain write-only through `chat.edit`/`chat.delete` (no composer injection). Character cards can be created, edited field-by-field and deleted (chats kept), but there is no avatar upload or import.
- SillyTavern's in-memory world cache cannot be evicted for a deleted book (no delete function is exposed), so reads immediately after `worlds.remove` may return cached data until reload. Writes go through `saveWorldInfo` to keep the cache correct for create/import/rename.
- `worlds.rename` refuses when a character card points at the book or it is globally activated (`WORLD_IN_USE`) rather than renaming and breaking the reference; with `migrateCards: true` (and the separate `host.characters.write` grant) it rewrites bound `extensions.world` links before deleting the old book, while embedded `character_book` copies still block. Chat and persona bindings are migrated.
- World books can be exported (raw host data, detached) and imported into a new name; import never overwrites, and validates entry shape/size before writing.
- `worlds.remove` is irreversible: protection is the separate `host.worldinfo.manage` permission, the consent prompt and the `confirm` echo — there is no soft delete, backup or undo, and no dedicated UI confirmation dialog (recorded as an open product question).
- World-book creation and deletion call SillyTavern's `/api/worldinfo/{edit,delete}` endpoints because `getContext()` exposes no equivalent; a host release that moves those endpoints would break those two capabilities (reads are unaffected).
- `chat.append`'s type allowlist follows the host's **templates**, not its type enum: `generic` (default) and `assistant_note`. SillyTavern 1.19 has no template for `narrator`/`comment`, so those types are rejected before any host call. The real append path is verified on a scratch character's chat; the harness never writes into the user's open chat.
- `chat.edit`/`chat.delete` are verified for real by the browser harness on a scratch character's chat (edit → file contains the text → delete → file no longer does), so the destructive path does not depend on the persona-less append hazard above.
- The character card write goes through `/api/characters/merge-attributes`, which writes the V2 `data` block only: tools that read legacy V1 fields without `data` see stale text until the host normalises the card. `characters.update` also cannot create or delete a card, and the in-memory copy is refreshed through `getCharacters()` (a card that still shows old text fails with `CHARACTER_UPDATE_FAILED`).
- The world entry defaults mirror SillyTavern 1.19.0's `newWorldInfoEntryTemplate`; a host upgrade that changes the entry model must update `WORLD_ENTRY_DEFAULTS` in `Loom Host/index.js` or new entries will be missing fields.
- Identity fingerprints are non-cryptographic (`fnv1a64`), and for packaged extensions they now cover the manifest plus the entry source (generated by `npm run extensions:index`); scripts hash their source. A package that loads extra files at runtime is not fully represented, and authors are self-declared identifiers, not verified accounts. No online trust/registry or migration flow yet.
- Data types are registered by identity (`extensionId:typeId`) but schemas are advisory names, not structural contracts; composite components re-create their nested view on update, so focus/scroll inside a large composite resets on prop changes.
- Permissions are an access constraint, not a sandbox: all scripts share the page realm, so a hostile script can grant itself permissions or bypass Loom entirely via `SillyTavern.getContext()`. There is no consent prompt yet — a user must open the panel and toggle a grant — and the caller identity is self-declared.
- Core state is per-extension and persisted when a store is attached (`setStateStore`); the host stores snapshots under `extensionSettings.__loom.state[extensionId]`, so state survives a reload. Only `structuredClone`-able values are persisted; live values stay in memory and are skipped. Events remain page-scoped by design. State sharing still requires exposing a capability.
- No cross-extension version/compatibility negotiation yet.
- UI system: `setProps` updates in place, `setChildren` reconciles children by `key` (or index + component) so matched items keep their element, listeners and state, and only `setRoot` rebuilds a whole tree. Serialization round-trips (handlers stripped, keys kept). `modal` and `tabs` are controlled components: interaction reports intent, the declared props decide the visible state. Remaining gaps: no virtualisation, no handler-closure rebinding beyond the node's current `on`, and moved items lose element-level scroll positions.
- Manifests are JavaScript objects passed in code; there is no file discovery, no dependency version constraints, and loader state is in memory (every reload starts at `loaded`).
- Mobile support is currently "mobile-safe, not mobile-optimized": layouts are fluid, tap targets are ≥44px, safe-area insets are respected, grids collapse at ≤768px, and `viewport.get` exposes width/isMobile. Not yet covered: touch gestures (swipe/drag/long-press), on-screen keyboard viewport changes, virtualized long lists, and dedicated phone layouts for dense panels.
- The world-book manager is a demonstrator: one entry at a time, no create/delete, no search, and its panel is fixed-position DOM owned by the extension (a second extension would collide in the same corner; a shared panel slot is a future UI item).
- Do not express breakpoints through CSS custom properties inside media queries (browsers ignore them); use literal values and keep them documented.
- Host events carry only `{ source, event }` and never host payloads. Chat message contents and user settings are not exposed.
- `characters.list` and `worlds.list` return complete lists with no pagination; large libraries render slowly in UI-driven consumers.
- In-page extension unload does not exist in SillyTavern, so cleanup runs on explicit unregister or page reload.
- SillyTavern has existing user modifications; avoid modifying or reverting them.
