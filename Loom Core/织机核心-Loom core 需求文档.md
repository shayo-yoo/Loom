# Loom Core 需求文档

文件名： `CoreCORE_REQUIREMENTS.md`

## 一、Core 的定位

Loom Core 是整个框架的基础运行与能力提供部分。

Core 不负责具体业务功能，而是提供读取、计算、执行、注入四种基础能力，并为脚本、UI 和扩展提供统一的调用接口。

Core 应尽可能保持精简、独立和可扩展。

它不应该随着上层扩展数量的增加而无限膨胀。

## 二、核心职责

### 2.1 读取

Core 应能够读取 Loom 运行过程中需要的数据。

包括但不限于：

- SillyTavern 的角色卡。
- 世界书及其条目。
- 当前聊天和聊天记录。
- 用户配置。
- 扩展自身的数据。
- 其他扩展公开的数据。
- 宿主环境提供的数据。
- 其他允许接入的数据来源。

应允许通过适配器、声明或其他合适的方式描述外部数据的读取方式。

Core 不应假设所有外部数据都是相同的 JSON 结构。

需要区分数据的读取、解析、转换和语义定义。

数据能够读取不代表它可以直接修改。

### 2.2 计算

Core 应提供必要的逻辑处理能力。

包括：

- 条件判断。
- 数据转换。
- 基础计算。
- 数据筛选。
- 结果处理。
- 其他通用计算操作。

复杂业务逻辑应由扩展脚本实现，不要求 Core 内置专用业务引擎。

### 2.3 执行

Core 应能够执行脚本和操作请求。

包括：

- 调用已注册的功能。
- 执行扩展提供的动作。
- 修改允许修改的数据。
- 调用宿主环境能力。
- 触发其他扩展公开的操作。
- 返回执行结果和错误信息。

执行接口应具有明确的输入、输出和错误反馈约定。

### 2.4 注入

Core 应负责将 Loom 的能力接入 SillyTavern 及其他允许接入的环境。

包括：

- 脚本运行所需的环境接入。
- 数据和事件接口接入。
- UI 所需的宿主挂载能力。
- 对酒馆原生功能的适配。
- 必要的外部能力接入。

注入的具体实现应尽可能与业务逻辑分离。

## 三、脚本运行与扩展调用

Core 应提供脚本调用 Loom 能力的基础环境。

主要支持 JavaScript，并为 TypeScript 开发提供合理支持。

TypeScript 可以通过编译或适当的开发工具链转换为 JavaScript 运行。

不要求用户必须安装独立 SDK。

脚本应能够：

- 调用 Core 提供的基础能力。
- 使用 Loom UI。
- 读取和修改允许访问的数据。
- 订阅和响应事件。
- 注册自己的公开接口。
- 调用其他扩展提供的接口。
- 接收操作结果和错误反馈。

脚本内部可以自由组织业务逻辑，不要求 Core 理解其具体实现。

## 四、能力注册与扩展接口

Core 应允许扩展注册自己提供的能力。

注册信息应能够明确说明：

- 提供者身份。
- 能力身份。
- 能力名称与用途。
- 输入参数。
- 输出结果。
- 调用方式。
- 必要的依赖关系。

不同扩展提供的能力应具有稳定、可区分的身份标识。

不能仅凭显示名称识别能力。

Core 应能够处理重复注册、身份冲突和接口不兼容等情况。

具体的高级依赖管理、可视化管理界面和资源市场不属于 Core 的强制内置职责。

## 五、数据结构与数据适配

Core 应支持扩展定义自己的数据类型和结构。

Core 只需要理解基础的数据组织和操作规则，不需要预先知道所有业务数据的具体含义。

例如，一个扩展可以自行定义任务、角色关系、剧情节点或其他业务对象。

其他扩展可以通过公开接口引用这些对象。

对于外部宿主数据，应尽可能通过适配器和统一的数据描述方式进行接入。

当 SillyTavern 的数据结构变化时，应尽量将兼容性修改限制在对应适配器中，避免迫使所有上层扩展同时修改。

读写能力应分别定义，不允许默认将只读数据当作可写数据处理。

## 六、事件与状态

Core 应提供必要的事件和状态基础能力，以支持扩展与 UI 协作。

包括：

- 接收宿主事件。
- 注册事件监听。
- 向扩展传递事件。
- 传递操作结果。
- 提供必要的状态读取和更新接口。
- 允许扩展管理自己的业务状态。

Core 不应将所有业务事件和业务状态预先固定。

具体业务事件由扩展根据需要定义和组合。

## 七、与 UI 的协作

Core 不负责具体界面绘制。

但应向 UI 提供必要的接口支持，包括：

- 数据请求。
- 操作执行。
- 状态同步。
- 事件通知。
- 结果反馈。
- 宿主界面挂载和必要的环境信息。

UI 不应直接依赖 Core 的内部实现，而应通过公开接口协作。

## 八、运行稳定性与基本约束

Core 应提供基本的错误处理和运行管理能力。

包括：

- 扩展加载失败的处理。
- 接口调用失败的反馈。
- 无效参数的识别。
- 重复注册的检测。
- 扩展卸载时的资源清理。
- 必要的运行状态管理。

Core 应保留不可被普通扩展绕过的基础访问约束。

但本项目不以构建完整安全认证系统为目标，不要求实现专业在线平台级别的安全体系。

## 九、可扩展性要求

Core 应允许未来增加新的通用基础能力。

新增能力应尽可能通过明确接口接入。

只有在确实需要新的底层机制时，才修改 Core 的核心实现。

新增能力时，应考虑现有脚本、扩展和 UI 的兼容性。

## 十、非目标

Core 不应直接承担以下职责：

- 具体世界书管理业务。
- 世界书触发规则编辑器。
- 具体角色管理业务。
- 具体聊天自动化业务。
- 通用 UI 组件的视觉设计。
- 可视化 UI 编辑器本身。
- 扩展市场和在线发布平台。
- 完整的专业安全认证体系。

这些功能可以由 Loom 扩展实现。
